# 評測文規格（Review Post Spec）

適用：作者評測別人做的模型、工具、產品（例：新模型上線後的實測）。
不適用：作者自己做的工具（走 `tech-share-post-spec.md`）、社群貼文改寫、週報、短觀點文。
通用欄位、檔名、圖片路徑、私人名字去識別化以 `article-spec.md` 為準；本檔只規範這一類文章的骨架與紀律。
範本文章：`src/data/blog/zh/gpt-6-1-terra-review.md`（2026-10-27）。

## 1. 主軸

整篇只回答一個問題：「這個東西值不值得用、用在哪？」搭時事的文章，開頭第一段就講它發布了什麼、賣點是什麼，再給結論。評測、比較都是為了回答這個問題；與被評測對象無關的發現（例如兩個別家模型之間的差距）最多一句，不開專段、不進表格。

## 2. 骨架（順序固定，H2 分節）

1. **開場（無標題）**：發布了什麼（日期、價格、定位）＋我的結論，一段講完。
2. **官方怎麼介紹**（H2）：只用官方原文與第三方評測。每個說法附出處連結，標明是官方還是第三方的測試。官方拿來比的對象要寫出來。
3. **我怎麼測、測到什麼**（H2）：先用兩句話交代範圍與樣本（幾題、每題幾次、用什麼資料、沒測什麼），只在這裡講一次。之後每組測試一段：只寫做了什麼、得到的數字。效果小或沒效果也寫。
4. **跟各家比**（H2）：以被評測的對象為中心，逐一對上每個比較對象。一張表放數字。
5. **建議**（H2）：分「交給它」「交給它但要驗收」「不要交給它」。每條講清楚做什麼、為什麼。
6. 結尾一句短促收束。不寫小結、結語、總結昇華。

## 3. 資料與來源

1. 網頁抓不到時用 `obu`（open-browser-use）當最後 fallback，先試過再下結論；不拿二手摘要當官方說法。用法見 memory `feedback_obu_fallback_no_hedging`。
2. 官方說法、第三方說法、我自己的實測，三者分開寫、分開標註。官方的數字是官方自己的測試，不當成中立結果。
3. 數字只用可查的紀錄與頁面；查不到就不寫，不補、不估。
4. Reddit、X 上的網友說法：找得到原文才引，附連結；找不到就不寫，也不在文中提「找不到」。

## 4. 語氣

1. **不寫防禦或免責語氣。** 禁：「老實說」「只代表…不代表…」「我這邊抓不到」「僅供參考」「限制很明顯」「當然」「不過要注意」這類。限制（樣本大小、沒測的項目）集中在「我怎麼測」開頭用兩句交代，之後不重複。
2. 結論直接講，不加保留語。數字就是數字。
3. 第一人稱口語，句子短，轉折用「但」。術語用英文原文，不解釋基本術語。
4. 禁「不是 A 而是 B」、金句、排比、emoji、「讓我們」、「值得注意的是」。不推測模型為什麼這樣表現，除非有紀錄支撐。
5. 寫完跑 `threads-voice/scripts/check_draft.py check --acct 主帳 --mode 資訊`，「必改」項照改。

## 5. 圖

1. 正文 3–5 張，依 `article-spec.md`「主動配圖」用 `.claude/figure-kit/`。
2. 值得畫的：價格對照、速度與額度對照（長條）、各題得分（表）、派工建議（分流）。只畫有數字或有判斷的東西。
3. 圖上的數字要與正文一致；正文數字改動，圖要重畫。
4. en 另畫一張（檔名加 `-en`），圖內不得有中文。

## 6. 隱私

不寫學員、客戶名、題庫具體題目、內部路徑與代號、commit hash。實測場景寫成通用描述（例：「讀聊天截圖判斷誰還沒被回覆」）。

## 7. 雙語

先寫 zh，定稿後交 agy 翻 en，段落、圖的順序一一對應；翻完用腳本比對數字集合。
