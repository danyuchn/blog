每次有新模型推出，網路上就開始吵「哪一家 AI 最強」「哪一個模型已經過氣了」。如果你平常工作會用 AI 寫教材、整理會議紀錄、擬企劃書，打開選單看到一長串模型名字，還有各種可以調高調低的「思考強度（effort，也就是讓 AI 在回答前先在腦中反覆推敲多久的開關，調越高想越久、扣的額度也越多）」，大概只會覺得頭痛：到底該選哪一個？

很多人的直覺是「既然付了錢，當然全部開最強、最貴的那個，思考強度也直接拉到頂」。結果往往是週三、週四就收到系統通知，每週額度已經見底；或者反過來，為了省額度全程用便宜的模型，卻發現它怎麼講都聽不懂你的弦外之音，來回修改花掉的時間比自己寫還久。

下次再有人跟你爭哪一家模型最強、哪一家是垃圾，你可以直接回他：小孩子才做選擇，我全都要。

真正好用的做法，從來不是找一個萬能的 AI 從頭做到尾，是把你手上的不同模型（AI 公司訓練出來、能力與收費高低不同的大腦版本，就像公司裡不同職級的員工）當成一個小團隊來帶。誰負責聽懂你的需求並發號施令、誰負責照著規矩把苦工做完、誰只在卡關時出來指點迷津，甚至哪一家廠牌負責聽錄音、哪一家負責做圖，都有各自最划算的位置。

這篇文章把我自己每天在跑的分工方式整理成一套沒有程式背景也能直接搬去用的工作流。前面先講「怎麼分派工作、明天可以怎麼試」，最後一節再把我自己踩過坑之後設好的進階自動化設定（指令與防呆機制）收在一起，給有在用進階工具的人參考。

## 第一層分工：同一家 AI 裡面的「幕僚、基層、老顧問」

先看我自己最常當作主力的 Claude。現在選單裡同時有 Opus 5.5、Sonnet 5.5 和 Fable 5.1 三個主力模型，很多人拿到手第一個問題就是：這三個到底差在哪？特別是 Opus 5.5 的能力已經比 Fable 5.1 強了，為什麼還需要 Fable？

以前舊版本（4.6 時代）的模型，彼此差的是「純智力」；但到了 5.5 這一代，我自己天天相處下來，感受最明顯的是「主動度」與「視野」的差別。用公司裡的角色來比對最清楚：

| 模型名稱 | 在團隊裡的角色 | 個性與強項 | 最划算的出場時機 |
|---|---|---|---|
| **Opus 5.5** | **成熟老道的幕僚（總指揮）** | 很會「適度讀心」，能從你給的背景脈絡抓出真實意圖，主動去想「你可能還需要什麼、下一步還能怎麼做」，而且比前代更會講人話、更省額度。 | **每天親自跟它對話的主力**。負責理解需求、拆解步驟、驗證成果與最後拍板。 |
| **Sonnet 5.5** | **聰明但厭世的基層（執行員）** | 能力完全夠把事情辦好，但只會辦到你交辦的「字面程度」，語氣也比較冷淡，不會多替你想一步。 | **交辦規格已經寫清楚的例行任務**，或是讓總指揮在背景派工給它跑腿，別自己跟它長篇大論聊天。 |
| **Fable 5.1** | **視野極廣的外部導師（顧問）** | 雖然一段時間沒更新，但知識邊界比 Opus 更廣，能看到「你根本沒想到要問」的盲點，卡關時能跳出框架想出更簡潔的解法。 | **太貴了，不要全程開**。只在開頭定大方向、中途卡關救火、或最後挑毛病驗收時請出場。 |

為什麼我會說平常「親自對話」一定要留給 Opus 5.5？因為我們在交代工作時，通常會帶一點背景脈絡，希望對方聽懂背後的真正目的。這種「適度讀心」的能力對我來說非常關鍵——我拿同樣帶脈絡的指令去跟 GPT 6.1 sol 講，它就看不太懂，只會死板地按字面辦事（GPT 6 更不用說），但 Opus 5.5 就能掌握得很好。

我前陣子好久沒直接跟 Sonnet 5.5 聊天，試著親自跟它對話處理事情，結果沒幾句就馬上退回 Opus 5.5。這不是說 Sonnet 能力不好，它一樣能把任務完成，但因為它讀心能力弱、凡事只做到字面要求，你親自跟它一來一往溝通，很快就會覺得有點煩。

## 第二層分工：跨廠牌的「大腦＋專科外包」

搞定了同一家模型的內部職級，下一個問題是：那還需要訂 Gemini 或 ChatGPT（GPT / Codex）嗎？

我的做法是讓 Claude 當整套工作流的「大腦中樞」，因為它在拆解長任務、呼叫工具跟寫程式上最穩；但它也有明顯的短板——它吃不了語音跟影片，處理超大份文件的成本也比較高。這時候就把其他廠牌當成「專科外包」接進來：

| 廠牌工具 | 在跨廠牌團隊裡的角色 | 我固定交給它的工作 |
|---|---|---|
| **Claude（Opus / Sonnet / Fable）** | **大腦中樞** | 聽懂我的需求、拆解長任務、把工作分派給其他工具，最後把各家做完的結果撈回來整合。 |
| **Gemini** | **長文清洗與多模態之王** | 處理「多模態（Multimodal，也就是除了讀寫文字外，還能直接聽語音、看影片、讀圖片與辨識版面的能力）」與海量資料：會議錄音轉逐字稿、看影片、圖片文字辨識（OCR）、排版檢查、還有動輒 200 頁的 PDF 摘要與大量資料清洗，划算又快。 |
| **GPT / Codex** | **備用大腦與視覺生圖** | 負責提供不同視角的第二意見審查、卡關時幫忙救援，以及生圖（目前 GPT Image 2 做社群分享圖卡還是最強）。 |

## 三個讓你省下一半額度、品質卻更好的派工原則

不管你用的是網頁版聊天介面，還是進階的自動化工具，只要抓準下面這三個派工原則，就不會再發生「額度莫名其妙見底、做出來的東西卻還是不合用」的慘劇。

### 1. 最貴的「顧問模型（Fable）」只在三個時刻請出場

我感覺 Fable 5.1 訓練時讀過的底層知識量可能更大，世界觀比 Opus 5.5 更廣。同一件事丟給它，它常常會自己提出一些我根本沒想到要問的邊界問題。但因為它的額度實在太珍貴，千萬不要拿來跑全程，我自己體感最好的出場時機只有三個：

1. **開頭定方向與最後驗收**：當你手上的任務還沒有清楚路線時，開頭先請 Fable 規劃整體架構，中間繁瑣的執行交給一般模型去跑，做完最後再拿回來給 Fable 驗收。
2. **中途卡關或需要「挑毛病」時當一次性顧問**：這是我後來最常用的模式。路線已經很清楚、只剩少數幾個難題時，平常用 Opus 或 Sonnet 往前推，遇到卡關死胡同，或是需要做「對抗式審查（故意請另一個 AI 站在反方立場、專門挑這份方案的漏洞與盲點）」時，才臨時請 Fable 出來給一次第二意見。Opus 5.5 遇到困境的時候，Fable 5.1 永遠是那個可以跳出框架，想出更優雅、更簡潔解法的模型。
3. **每週額度快重置前，發現還剩一堆沒用完的時候**：明天系統就要把每週額度歸零重置了，這時候不用白不用，直接開 Fable 來想長期的大問題。

我自己前陣子在整理 GMAT 教學的服務流程規格，就是照這套流程跑：先派 Sonnet 把 `61` 份散落的歷史資料抽出來，交給 Opus 寫成完整的流程規格書，最後再請 Fable 審過一輪；每週例行檢查要砍掉哪些多餘的工作步驟時，我也是先讓 Fable 做一輪對抗式審查，看完它挑出的盲點後，再由我自己拍板。這種時候 Fable 的視野對我來說更像一個導師。

### 2. 別無腦把「思考強度」開到最高檔——基層開最高檔比主管還貴

很多人以為「便宜的模型開最高強度，一定比貴的模型划算」，或者不管做什麼事都把思考強度拉到最滿。這其實是最常見的額度殺手。

Sonnet 5.5 剛發布大概 `15` 小時的時候，我去 Reddit 翻了一輪國外使用者的實測風向。剛發布當下大家超興奮，一堆人在分享一個指令就生出賽車遊戲（Mario Kart）、`49` 分鐘做完 3D 殭屍射擊遊戲，或者在寫作「基準測試（Benchmark，拿同一套標準考題去考不同 AI，看誰分數高的公開評比）」排到第 `2` 名，只輸給 Opus 5.5。

但過了幾小時，開始有人把跑分跟帳單拆開來看，發現了兩個關鍵事實：
- 那個宣稱「Sonnet 打贏 Opus（`70.6%` 對 `66.4%`）」的測試（Terminal-Bench），兩邊開的思考強度根本不一樣，不能直接拿來互比。
- 有人貼出實際跑題目的帳單：把 Sonnet 5.5 的思考強度開到最高檔（Max），每題大約要吃掉 `$7.60` 美金的「額度（Token，AI 計算閱讀與產出字數的計費單位，可以直接想成你被扣掉的點數與金額）」，竟然比 Opus 5.5 開最高檔的 `$5.98` 美金還要貴！

我自己實測的結論也跟社群共識完全一致：
1. **千萬不要把 Sonnet 5.5 亂開到最高檔（Max）**：想開最高檔，不如直接開 Opus 5.5 的中高檔位，做出來更好還比較省錢。Sonnet 所謂「便宜一半」的優勢，只有在開低檔（low）或中檔（medium）時才成立。
2. **Sonnet 5.5 的甜蜜點是「中檔強度＋寫好的標準流程」**：我曾故意讓 Sonnet 5.5（開高檔 high）在不給任何「固定工作流／技能包（Skill，也就是預先寫好給 AI 照著走的標準作業流程說明書）」、也不用輔助工具的情況下，純靠自己從頭做出一支產品示範影片。結果它雖然做得出好成品，但中間考慮到的細節明顯比較少，來回修改的輪次變多、更耗額度，而且動不動就停下來要人幫忙介入。反過來說，如果先讓 Opus 5.5 幫你把標準流程或規格寫清楚，再交給開中檔（med）的 Sonnet 照著做，它比較不會亂加東西，這時候才能真正省到額度。
3. **連主力 Opus 都不必開到頂**：在 Opus 5 上如果把思考強度開到極高（xhigh 或最高檔，包含以前會強制拉到極高強度的 Ultracode 模式），它會有個「想太多（overthink）」的壞毛病——自己在腦子裡左右互搏，狂燒你的額度，但最後寫出來的東西跟開高檔（high）幾乎沒有差別。我自己平常連 Opus 都最多開到中檔（med）或高檔（high）就夠了（關於各檔位多花多少錢的實測數據表，我放在文末技術專區）。

### 3. 把 AI 分身當員工在管：立下「請誰要先講、超過兩人要簽核」的規矩

當你開始會讓主 AI 在背景派分身（Subagent）幫你平行處理任務時，最容易踩到一個大坑：主 AI 在叫分身的時候，如果沒有明確指定分身要用哪個等級的模型，系統預設會「直接繼承主 AI 的等級」。

我就曾經踩過一次慘痛的地雷：那次我開著最貴的 Fable 在聊架構，結果 Fable 轉頭一口氣幫我派了 `3` 個分身去查資料——因為沒有指定等級，那 `3` 個分身全部繼承了 Fable 的最高等級（等於同時請了三個頂級顧問去跑腿抄資料），我的每週額度在幾分鐘內瞬間燒乾。

從那次之後，我就把 AI 分身徹底當成公司的員工在管，立下三條鐵律：
- **派工時必須明講要請哪個職級的人**：是叫基層（Sonnet）還是主管（Opus）？不准不講就預設叫最貴的人出去跑腿。
- **同時最多只能叫 `2` 個分身做事**：原則上一次就是兩個人平行處理；如果要叫到 `3` 個以上，系統必須先攔下來問我同不同意，而且主 AI 必須先跟我說明為什麼這件事非得叫這麼多人不可。
- **禁止分身自己再往下找外包**：不准分身在背景自己又派分身，避免在你看不到的地方無限繁殖燒額度。

简单來說，就是跟員工講清楚：「公司原則就是一次派兩個基層，要加人、要升等，先寫理由報給我簽核。」

## 明天就可以試：我自己的「一週兩種模式」工作節奏

如果你讀到這裡，想問：「我沒有裝那些複雜的程式工具，只是平常訂了付費版 AI 在工作上用，明天開始可以怎麼試？」

除了下次開口前先分清楚「這件事該找幕僚（Opus）、基層（Sonnet）還是顧問（Fable）」之外，我最推薦你試試看的是**用一週的時間節奏來分配額度**。

摸清了各模型的脾氣跟額度消耗規律之後，好好笑，我發現我自己已經不知不覺養成了一套固定的每週循環：

- **週一到週四（效率王模式）**：這四天專心衝刺日常營運與例行事務。因為平常要做的事（備課資料整理、客戶信件草稿、例行報表）流程都已經固定下來了，我就用中低檔位的 Sonnet 搭配寫好的標準流程（以及前面提到的 Gemini 等外包工具）一路高效清待辦。所以我的客戶都是週一到週四聯絡的，這四天效率拉滿，而且額度省到不行。
- **週五到週日（遠見創造力模式）**：到了週五一看面板，突然發現前四天實在太省了，每週額度還剩一大堆沒用完！這時候我就會直接打開最貴的 Fable，切換成創造力爆發的遠見模式——拿來對未來的工作做長期探索、規劃新專案架構、檢討並改善現有的工作流程。所以我所有新的研發與大型交付成果，幾乎都是週五到週日長出來的。
- **週日下午五點（收斂模式）**：眼看這週的額度差不多用完了，準時收心變回省額度的保守模式，準備迎接下週一重新開始的循環。

給大家看一張我週日手機上的真實額度面板截圖：

![手機上的額度面板：目前 session 用掉 92%、全模型週限額用掉 97%、Fable 專屬額度只用掉 47%](/blog/assets/posts/when-to-call-fable-and-effort/1-weekly-rhythm.jpg)

你看，當下時段（session）用掉 `92%`、全模型每週總限額用到了 `97%`，用得乾乾淨淨一點都不浪費；但因為前面四天有做分工，最貴的 Fable 專屬額度居然只用掉 `47%`，完全不會發生週三就卡死動彈不得的窘境。

明天早上打開 AI 之前，你不妨也先把下週的工作分成兩堆：已經有固定做法的例行公事，週一到週四交給一般模型照表操課；需要跳出框架想新點子、找盲點的難題，留到週五再請最聰明的顧問出場。

## 進階技術專區：給想自己動手設定自動化與防呆護欄的人

如果你也是使用 **Claude Code（CLI，也就是在電腦終端機裡直接操作檔案、執行任務的命令列 AI 工具）** 的進階使用者，前面提到的所有分工、檔位控制與防燒乾鐵律，其實都可以直接寫進你的 **工作環境與護欄設定（Harness，包在 AI 外面、用來規定它能做什麼與不能做什麼的規則檔與防護機制總稱）** 裡，讓系統自動幫你把關。

以下整理我自己在終端機環境裡的實際配置與技術細節：

### 1. 規劃與實作自動切換的隱藏指令：`/model opusplan` 與 `/advisor`

在 Claude Code CLI 裡面有一個很實用的冷知識代號：輸入 `/model opusplan`，系統就會自動在「規劃階段（Plan Mode）」使用 Opus 5.5 幫你把架構跟步驟想清楚，一旦進入「動手實作階段」就自動轉交給 Sonnet 執行，省下你自己手動切換的麻煩。

而當主線用 Opus 5.5 或 Sonnet 跑到一半卡關，需要請 Fable 5.1 出來給策略上的第二意見時，不用把整個主對話切去 Fable——因為在同一個對話中途直接換模型，會遇到 **快取失效（Cache Miss，也就是原本已經讀過的背景資料要重新計算一次，導致多扣一大筆額度的現象）**。比較省額度的做法是用 `/advisor` 或是派一個單次的 Fable subagent 出來當臨時顧問，審完就把結果帶回主線。

另外，Opus 5.5 在面對 **長上下文壓縮（Compaction，當對話太長時，系統自動把前面的聊天紀錄濃縮成重點摘要，好讓對話能繼續下去的機制）** 之後，它對使用者真實意圖的「讀心準確度」依然沒有跑掉多少（這點就不確定是底層模型本身強，還是 Claude Code 的環境設計強了）。

### 2. 為什麼別把 effort 開到 xhigh / max？內建成本倍率表與 Ultracode 更新

前面提到不要無腦把思考強度（effort）開到頂，Reddit（r/ClaudeAI）上有網友直接從 Claude Code 原始碼裡挖出了一張內建的各模型、各 effort 等級的 token 成本倍率表，還自己拿真實專案實測了一輪（[Reddit 原文連結](https://www.reddit.com/r/ClaudeAI/comments/1wjr89j/claude_code_ships_a_permodel_table_of_what_each/)）：

![Reddit 貼文截圖：Claude Code 內建的各模型 effort 成本表，以 high 為 1。Opus 5 從 high 到 xhigh 多 60%，xhigh 到 max 只再多 6%](/blog/assets/posts/when-to-call-fable-and-effort/effort-cost-table.jpg)

![同一篇貼文的實測：8 個 Opus 5 agent 在同一個 repo 跑兩個真實任務、四種 effort，xhigh 與 max 的輸出 token 幾乎一樣](/blog/assets/posts/when-to-call-fable-and-effort/effort-cost-measured.jpg)

從這兩張圖可以看到兩個很硬的數字：
- 以 `high` 檔位為基準 `1` 來算，Opus 5 從 `high` 往上升一級到 `xhigh`，消耗的成本會直接暴增 `60%`；從 `xhigh` 再升到 `max` 則多 `6%`。
- 該網友用 `8` 個 Opus 5 agent 在同一個程式碼儲存庫（repo）跑了 `2` 個真實任務、測試 `4` 種不同 effort，結果發現 `xhigh` 與 `max` 輸出的 token 數量幾乎一模一樣。

> **版本更新補充（2026-10-20）**：在舊版裡開啟 Ultracode 會強制綁定跑在 `xhigh` 高耗能模式；不過在 Claude Code `v2.1.284` 之後，Ultracode 已經變成 `/effort` 裡面一個獨立的開關，不再強制拉到 `xhigh`，開著時就會照你當前設定的 effort 等級去跑。

### 3. 防護額度燒乾與越權寫檔的兩道攔截器（Hook）

在派發 subagent 時，為了避免前面提過「Fable 沒指定模型、預設繼承派了 3 個 Fable subagent 瞬間燒乾額度」的慘劇，以及防範 Sonnet 5.5 的一個小毛病——**拿 Sonnet 5.5 當調查型（唯讀查找）子代理時，它常常會手癢越權去改寫檔案**——建議在你的環境設定（harness）裡做好三件事：

1. **加上「強制顯式指定模型」的攔截器（Hook，也就是在 AI 準備執行某個動作前自動跳出來檢查、不符合規定就擋下來的自動把關程式）**：設定一道 `PreToolUse` hook，只要主 agent 呼叫 subagent 時漏填模型名稱（企圖繼承預設值），就直接攔下來報錯，強迫它必須明確寫出要用 `haiku`、`sonnet`、`opus` 還是 `fable`。你可以直接把下面這張圖存下來丟給你的 Claude Code，叫它照著幫你設好：

![Claude Code 的 PreToolUse hook 擋下沒有指定模型的派工：錯誤訊息要求顯式指定 haiku、sonnet、opus 或 fable，不准繼承主 agent 的預設](/blog/assets/posts/when-to-call-fable-and-effort/subagent-model-hook.jpg)

2. **關閉多層嵌套分身（nested subagent）並限制並行數量**：去設定檔把 nested subagent 關掉，不讓分身再自己派分身。同時再設一道 hook 限制「同時運行的 subagent 最多 `2` 個」，一旦主 agent 想同時派 `3` 個以上，hook 就會攔下來要求你手動輸入 `Yes/No` 簽核；我同時也在規則檔（rules）的派工段落寫明「原則上最多兩個，要派更多請先說明理由」。
3. **在規則中限制調查型子代理的寫入權限**：如果只派 Sonnet 5.5 去查資料，記得在派工規則或權限設定中鎖死唯讀，避免它越權改檔。

### 4. 不切視窗呼叫 Gemini 與 Codex 的串接方式

在跨廠牌分工那節的影片裡，之所以可以全程留在 Claude 的工作畫面裡、不用自己開三個瀏覽器分頁複製貼上，是因為我在 Claude Code 裡裝了 **Codex Plugin**，並且把 **Gemini CLI / API 包裝成一個專屬的代理（agent）**（再加上本地端模型與夜間自動排程）。

這樣一來，當我丟出一個包含「讀 200 頁 PDF、聽錄音檔、寫企劃再做一張 IG 圖卡」的複合任務時，負責當大腦中樞的 Claude 就會自己判斷：把音檔跟長 PDF 派給 Gemini agent 處理、把生圖指令派給 Codex Plugin，等兩邊各自跑完，Claude 再自動把結果撈回來整合成最終成品。
