你有沒有遇過這種讓人血壓升高的狀況：為了怕自己或團隊出包，你特地設了一道「送出前檢查」——可能是請 AI 照著清單幫你審核每天要發的報表、請系統自動檢查題庫或教材有沒有漏字，或是設了一個自動化流程替檔案把關。

每天看到畫面跳出「檢查通過、0 個錯誤」，你就放心地把東西發出去。結果某天突然被發現：今天送出去的根本是昨天的舊報表、有 89 道缺了關鍵分類的題目居然被默默丟進一個沒人看得懂的角落，甚至只因為換了一個 AI 模型，原本完全正確的內容就被整批擋在門外。

以前我寫過兩篇文章談「怎麼驗收 AI 交出來的東西」——不要直接相信 AI 自己寫的「沒問題」摘要，也不要看到系統沒跳錯誤訊息就當作成功（想看這兩篇可點：[不要用 AI 的摘要驗收 AI](/blog/posts/zh/dont-grade-ai-by-its-summary)、[沒拋錯不代表成功](/blog/posts/zh/silent-failures-and-confabulated-tool-results)）。

這篇要往前提一步，談「怎麼設計把關規則」：當你要請 AI 或自動化工具當守門員（我們稱作「閘門」，也就是卡在流程中間、不合規定就不准往下一關走的檢查點）時，到底要怎麼設條件，它才不會淪為虛設的裝飾品？

下面這五個原則，每一條都是我自己先賠掉一次時間或差點出包，才換來的教訓。就算你完全不寫程式，平常只是用 AI 審核文件、請助教照表核對教材，或是管理團隊的交付流程，明天開始就能直接照這五點改。

## 明天就能試的五個把關設計原則

### 1. 檢查「今天沒重做就會露餡」的內容，不要只檢查格式在不在

很多人請 AI 或助教檢查每日報表、週報或例行文件時，定的檢查標準是：「看看那幾個大標題和段落有沒有齊全。」

但問題來了——**昨天那份舊檔案，也有一模一樣的標題跟段落。** 如果你只檢查格式跟結構在不在，萬一今天系統根本沒跑、或者有人不小心拿昨天的舊檔交差，這道檢查照樣會給你打勾放行，等於幫昨天的舊檔案發了一張永久通行證。

**明天你可以這樣試：**
當你請 AI 幫你把關例行文件時，規定它一定要核對**「只有今天真的重做過，才會變動的內容」**。例如：今天的日期、今天才會出現的新紀錄條目、或是每次更新都會改變的統計數字。只要這幾個欄位跟昨天一樣，就算格式再完整，也必須立刻退回。

### 2. 看到「零錯誤」先別高興，先故意塞一個假錯誤測它會不會叫

當我們請 AI 幫一份文件抓錯、或是檢查教材裡有沒有不該公開的機密資訊時，最危險的回答就是「檢查完畢，0 個問題」。

因為「0 個問題」有兩種可能：一種是你的文件真的非常乾淨；另一種是**你的檢查工具根本沒在動，或是搜尋條件完全設錯了**。反過來，有些檢查器則是「看字面不看上下文」，把你教材裡特地寫出來當作「錯誤示範」的句子，也當成真違規亂報警。

**明天你可以這樣試：**
在正式相信一個檢查流程（或一段審稿提示詞，也就是給 AI 的指令）之前，先做一次「雙向測試」：
- **塞一顆必爆的假地雷**：故意在文件裡塞一個你明知道違規的假資料或錯字，丟給 AI 檢查。如果它連這顆假地雷都沒叫，它後面說的「零錯誤」就完全不能信。
- **放一份確定乾淨的範本**：確認它不會連正常內容或教材裡的「反面範例」都亂抓。會漏叫跟會亂叫的守門員，兩邊都要先測過才能上崗。

### 3. 「挑出問題」不等於「攔下來」：沒讓流程停住，那叫報表不叫把關

這是所有人最容易自己騙自己的一條。你可能請 AI 在流程裡幫你列出所有不合格的項目，它也真的乖乖列了一長串清單給你看——但列完之後，系統或流程完全沒有停下來，那些被標記有問題的項目，照樣順順地流進了「正式發布」或「寄給客戶」的下一步。

把問題印出來是給人讀的「參考報表」；能讓整個動作當場煞車、不修好就不准按下一鍵的，才叫「把關」。

**明天你可以這樣試：**
檢視你手邊的工作流程或 AI 提示詞：當 AI 抓到錯誤時，預設動作是什麼？如果你讓 AI「一邊挑錯、一邊直接產出最終版」，人一忙起來根本不會細看中間的警告。請把規則改成：**只要發現任何一項不合格，就立刻停在原地、只輸出錯誤清單，絕對不准同時產出最終成品或進入下一步。**

### 4. 你沒明講過的格式，別拿來當退件標準

有時候我們請 AI 產出報告或整理筆記，心裡默默期待它的標題要寫成某種固定字樣，但我們在下指令（Prompt）時從來沒把這個格式規定寫進去。

可能你平常習慣用的 A 模型剛好猜中你的喜好，每次寫出來的標題都長那樣，久了你就把這個標題字樣設成自動驗收的標準。結果某天你換了一個更聰明的 B 模型，它寫出來的內容完全正確，只因為標題換了一種寫法，就被你的檢查關卡判定失敗，後面整套整理流程全部被跳過。

**明天你可以這樣試：**
檢查一下你的驗收標準裡，有沒有這種「我自己心裡想要，但從沒白紙黑字寫進指令裡」的潛規則。**指令裡沒規定過的東西，審核時就不該拿來當退件理由**；如果你真的很在意某個標題字樣或欄位名稱，請先回頭把它明明白白寫進最初的指令裡。

### 5. 守門員只能有「放行」或「退回」兩條路，不准「改個名字偷偷放旁邊」

這是最荒謬、也最難抓的一種漏洞：守門員遇到不合格或看不懂的資料時，既沒有放行到正式區，也沒有報錯退回給你，而是自己貼心地幫這些問題資料取了一個聽起來像「已通過」的新檔名，靜悄悄地塞進旁邊的資料夾裡。

因為全程沒有跳出任何錯誤警告，你以為所有資料都順利處理完了，直到最後對帳才發現有一大塊東西人間蒸發。

**明天你可以這樣試：**
不管你是設計 AI 自動化流程，還是跟團隊助教交代審核規矩，把出口死死鎖在兩個：**要嘛完全合格「放行」，要嘛不合格「退件並立刻通知」。** 嚴格禁止出現第三條路（例如「先把缺欄位的資料移到暫存區，等以後再說」卻不報錯），因為那不是在處理問題，是把問題藏得比完全不檢查還要深。

## 我自己怎麼被「沒擋住的閘門」坑過？

上面這五條，不是坐在書桌前想出來的理論，是我自己管每日自動簡報、整理線上題庫、還有準備公開教材時，連續踩雷踩出來的真實紀錄：

- **漏跑一天還照樣及格的每日晨報**：我有一套每天早上自動整理的晨報，原本的把關條件只檢查「那幾個固定的段落標題在不在」。結果有天晨報在沒報錯的情況下靜默漏跑了一天，檢查關卡看到昨天的舊檔案裡標題都在，就照樣判及格放行。
- **塞假金鑰才抓出掃描器有沒有在動**：某天我同一天內連續兩次被自己的檢查器騙——檢查器回報「0 個問題」，我就以為沒事了，後來才發現前面根本沒把要檢查的清單餵進去，檢查器收到空資料，吐出來的當然是 0。同一天在準備公開教材前做機密資料掃描，掃描器也回報 0；被騙怕了之後，我特地拿一把「假金鑰」塞進檔案裡反測，確認掃描器真的有抓到這把假金鑰，我才敢相信那個 0。反方向的誤報也在同一天發生兩次：一次是檢查器把課堂上當場才會產出的檔案當成「漏放的素材」，另一次是把教材裡已經改寫成「反面範例」的示範字句當成真違規，因為它只呆呆比對字面、完全沒看前後文。
- **印了警告卻照樣放行的檢查程式**：我有支清理資料的流程，設定了「先跑檢查程式，有錯就停下來」。結果那支檢查程式把問題通通印在畫面上之後，最後還是跟系統回報「執行成功」，導致後面攔截的機制完全沒觸發，被標出問題的項目照樣一路進了下一關。
- **換個 AI 模型就無辜卡關的筆記整理**：我原本沒在指令（Prompt）裡規定輸出的標題要長什麼字樣，檢查關卡卻拿特定的標題字面去逐字核對。平常跑 Claude Sonnet 模型時，它寫出來的字面剛好合格；結果一換成更高階的 Claude Opus 模型，標題寫法稍微不同就被判失敗，即便裡面的內容明明是對的，後面整段知識庫整理流程卻因此被直接跳過。
- **89 道題目被藏進「假裝通過」的幽靈檔案**：在處理線上題庫時，把關程式遇到漏標「題型分類」的題目，居然不是退件報錯，而是把它們寫進一個叫做「未定義_已通過」的檔案裡。檔名裡大剌剌寫著「已通過」，那 89 題就這樣過了關，卻因為檔名不是後面匯入系統認得的正式名稱，整批題目晾在旁邊沒人發現，全程零報錯。後來我是靠著檢查題目的結構形狀（確認有五個選項、沒有另一種題型的專屬句型、而且標題開頭對得上），才把那批問題解決題撈回來，沒讓它們整批漏掉。更慘的是，同一份流程在算進度時，把「待檢區」底下的備份檔案也一起重複算進去，導致顯示的完成進度直接虛報了一倍。

## 給進階使用者的技術細節：寫在腳本與 Harness 裡的四條硬判準

如果你平常自己寫 Shell Script、Node.js 腳本，或是在建構 AI Agent 的外層控制框架（Harness，也就是在 AI 模型外層負責派工、驗收與攔截的程式與規則集），這裡把前面五個故事背後的指令、離開碼（exit code）與檔案細節完整攤開來：

### 1. 閘門要綁「`no-op` 下活不下來的欄位」
- **技術踩坑點**：`no-op`（No Operation）指的是程式表面上跑了、實際上卻什麼動作都沒做的空轉狀態。晨報閘門如果只檢查 Markdown 的 H2/H3 段落標題存在，在 `no-op` 沒更新檔案時，昨天的舊檔結構完全合法。
- **實作判準**：驗證條件必須綁定 `today's date`、當日動態生成的 entry ID，或只有實際重跑才會改變的 hash / timestamp。

### 2. 檢查器回 `0` 之前，先做雙向反驗（Positive & Negative Controls）
- **技術踩坑點**：
  1. 用管線指令 `git rev-list | cat-file --batch-check | awk` 掃描 Git 儲存庫裡的大檔案時，回傳 `0` 不是因為沒有大物件，而是前段根本沒產出物件清單，`awk`（文字處理工具）收到空輸入，自然輸出 `0`。
  2. 跑完 `git filter-repo`（清理 Git 歷史紀錄的工具）之後的全物件掃描，也先跑出一份「假的乾淨」。
  3. 教材 repo 公開前的 secret scan（機密金鑰掃描）回傳 `0`，必須手動塞入一把假 API key 反驗，確認 scanner 真的會命中，那個 `0` 才算數。
  4. 同日兩次 False Positive（誤報）：一次把課堂當場動態產出的檔案誤判為缺漏的 `asset`（靜態素材）；一次把已經改寫為反例教學的字串當成違規，因為 regex / 字串比對沒看上下文語境。
- **實作判準**：當所有檢查「都沒叫」時，第一懷疑永遠是反驗 harness 自己沒接上，而不是資料很乾淨。測試套件必須同時包含「乾淨對照組（必須不叫）」與「已知破壞案例（每個都必須叫）」。

### 3. 只印訊息、不改離開碼（Exit Code），等於沒有閘門
- **技術踩坑點**：在批次清理（sweep）腳本裡寫了 `node check.js || exit 1`（在命令列裡，`||` 代表前面的程式執行失敗時，才執行後面的 `exit 1` 中斷流程）。表面上看起來是個標準閘門，但因為 `check.js` 把錯誤訊息印到終端機後，最後依然以預設的 `exit 0`（離開碼 0，向作業系統回報執行成功）結束，導致 `||` 後面的中斷指令永遠不會觸發，被旗標（flagged）出來的問題項目照樣流進下一步。
- **實作判準**：`stdout / stderr` 印出來的訊息是給人看的報表；非零離開碼（non-zero exit code，如 `process.exit(1)`）才是給自動化流程看的閘門。

### 4. 別把 Prompt 沒規定的字面當成 Schema 契約，也別讓 Fallback 變成靜默藏檔
- **隱性契約（Implicit Contract）**：當初換模型（從 `Sonnet` 換成 `Opus`）時，因為 Prompt 裡根本沒規定輸出標題的精確字面格式，閘門腳本卻拿硬寫的標題字串去逐字比對。`Sonnet` 的預設輸出剛好吻合，`Opus` 輸出不同字面就被判 fail，導致後續的知識庫整理管線被整段跳過。要驗某個欄位字面，就必須先把該格式寫進 Prompt 或 Structured Output Schema。
- **非法的第三出口與虛報計數**：題庫管線遇到缺少 `type` 欄位的題目時，沒有 throw error 退件，而是 fallback 改寫進 `undefined_passed.json`。因為檔名帶有 `passed` 且回傳成功，89 題就這樣靜默脫離主流程（匯入端只讀正式檔名，根本不認得 `undefined_passed.json`）。事後是靠形狀驗證（Shape Validation：檢查具備 5 個選項、不含 GMAT DS 資料充分性題型的句型、且標題前綴吻合）才把那批 PS（Problem Solving，問題解決）題目救回來。同時，進度統計用了 `find -name out.json`，沒有排除 `gate-in/` 輸入暫存資料夾底下的副本，導致完成進度直接虛報一倍。
