10/06 早上上課帶 Codex，慢到炸。都已經開 6.1 Sol low effort fast mode 了，還是慢到十幾分鐘才能回來看下一個 turn，雙開都解決不了現場的尷尬。

還好林北以前是 150 人教室的大班講台磨練出來的，我只能發揮傳統教學技藝，各種尬聊，聊規劃、聊理想、聊未來的架構，然後也故意打開我的 Claude Code 示範，讓客戶看看速度差距。

這場突發的慢速意外，其實就讓人意識到這兩家會輪流自作孽，平常心就好。如果公司未來要仰賴商業 AI 做 Agent，那就要做好備援，不然模型躺了公司也跟著躺了。

## OpenAI 逆風週期：砍速度、砍額度與算力挪移

OpenAI 最近確定是關了。砍速度，砍額度，什麼都砍，送重置已經被看破手腳。

X 上 @mylifcc 有一張實測截圖：Astra、5.6 Sol、Luna 的速度全部被降低到原來的 60%，GPT-6.1 Sol 更是降低到 15 tok/s。

![X 網友 @mylifcc 的實測截圖，統計各個 GPT 模型每秒輸出 token 數，標題寫 Astra、5.6 Sol、Luna 的速度全部降到原來的 60%，GPT-6.1 Sol 降到 15 tok/s](/blog/assets/posts/model-vendors-take-turns-failing/1-gpt-throughput-drop.jpg)

過去幾天 codex 慢到靠杯的元兇，看來就是這個？

![OpenAI 官方帳號貼文截圖：釋出一批由內部前沿模型產出的數學成果，附 openai/math 的 GitHub 連結](/blog/assets/posts/model-vendors-take-turns-failing/2-openai-math-release.jpg)

眼看他起朱樓，眼看他宴賓客，眼看他樓塌了。最近讓 GPT 6.1 Sol 做的事情中，我最滿意的是做這張梗圖：

![三格梗圖，標題依序為「眼看他起朱樓」「眼看他宴賓客」「眼看他樓塌了」，各貼一則 OpenAI 的 Tibo 的貼文：Codex 週用戶破三百萬並重置額度、Astra 提前上線並全面重置、重新開放 Pro 200 美元訂閱但用量計算改成實際只剩舊方案一半的 API 額度。圖底註明由 GPT 6.1 Sol 製作](/blog/assets/posts/model-vendors-take-turns-failing/3-codex-meme.jpg)

做正事又慢又卡，找素材、做 meme 圖臭自己東家竟然做得又快又好，果然是 OpenAI 口中最接近人類的 AGI。

6.1 在知識工作上一樣爛，我另外寫過[為什麼 GPT 6 Sol / Luna 用起來這麼蠢](/blog/posts/zh/why-gpt6-sol-luna-felt-dumb)。現在 codex 只能讓他去做爬蟲等單點任務了，我自己也是反覆搬家到很心累。

## 風向輪流轉：算力擠爆與封號的商業現實

兩三個月前，風向完全是反過來的：Anthropic 明明原本領先，為什麼會被 OpenAI 瘋狂搶走客戶？

Opus 5 上線的時候，本來想說他們很勇敢。後來想一想，Claude 一到日都有 outage 過，他們壓根就不在乎 uptime。

但現在 Anthropic 這邊則是前陣子要關過，最近又大門敞開了，尤其是 O 5.5，簡直 cp 怪物。以下是我最新的實測，[100 USD 開出 5469 大禮包](https://www.threads.com/share/BANRqG4Fs8/)。

所以我現在最大的願望，反而是希望 OpenAI 能夠稍微爭氣一點：

1. Anthropic 才不會一家獨大拿翹
2. OpenAI 才不會有更多人逃難過來把算力擠爆

拜託 OpenAI 快點振作，不然太多人逃難過來，到時候 Anthropic 算力不夠遭殃的又是我們。要不是 OpenAI 亂七八糟，Anthropic 哪敢那麼囂張。

判斷一間模型商什麼時候開始逆風，其實有一個很準的訊號：就是看他們是不是開始推各種花里胡俏的終端應用。想想 Claude Design 那時誇張的一天一上新，想想 OpenAI Sora 的社交短影音 App。當這些東西收斂、剪枝的時候，模型商才要開始順風。

講到封號，其實要逃真的很難，因為他們的數位指紋識別抓法設定，就是完全不在乎 Type 1 Error，拼了命的要降低 Type 2 Error，也就是「寧可錯殺一百，不願放過一人」。

從商業邏輯來看這很好理解：企業戶才是模型商的主要收益來源。訂閱戶是他們賠本 50 倍補貼的，但被假號蒸餾的巨大風險偏偏又來自這些訂閱戶，所以錯殺好幾百個也不會影響到整體收益。更何況兩大模型商在歷史上的重要上位時刻，靠的大多是對手的失誤；只要錯殺比例不要高到大屠殺等級，社群很難集體跳槽。

## 落地調校：磨平 Codex 的防禦式語氣

除了服務與額度輪流出問題，Codex 在日常使用上還有另一個困擾。之前看到一則諷刺寫得好好笑，這種防禦式寫作我看 Codex 的嫌疑很大：「好的，我會誠實揭露我的睡眠狀態。我會分清楚『閉目養神』、『淺眠』與『深眠』，不會把三種狀態合併計算。我也會用 SHA-256 驗證睡眠時長與夢境內容一致。」

在日常指令協作中，Codex 非常熱衷於使用「不能、不可以、不⋯不代表⋯」這種說話方式。我請 Claude 派助理去檢索過往的對話紀錄，抓 Codex 防禦性寫作的口癖：為什麼同一套跨工具同步架構下，Claude 就不會這樣，Codex 就會？

![終端機截圖：我請 Claude 派 subagent 去用 history-find 抓 codex 防禦性寫作的口癖，問是 harness 還是 base model 的問題，Claude 回覆接著派 subagent 去查 Codex 的口癖](/blog/assets/posts/model-vendors-take-turns-failing/4-codex-defensive-ask.jpg)

調查結果顯示，主因在 Codex 的底模本身，不在同步設定。但設定架構確實留了缺口，讓 Codex 缺少把語氣拉回來的正向導引。Claude 那邊有正向的風格設定，用正面描述說明要什麼語氣；Codex 卻只有預設的務實風格，其餘全是滿滿的禁止清單。另外還有一個可能的加成（推論，未實測）：「負向斷言必須驗證」這類規則，可能讓 Codex 把「查不到」固定寫成「不能推論⋯」這種防護句。

解決辦法是在 Codex 專屬設定檔頂層加入開發者指令，用肯定句先說結論與下一步，再補必要的限制。限制只寫一次，不另開澄清；未驗證的事陳述事實，不預防對方的誤解，讓語氣像資深同事交接一樣簡短確定。

拿 Codex 的原句試改兩句：

- 原句：「『明年初』不是確定日期，所以不能自行建一個 2027/1/1 的追蹤待辦。」改後：「『明年初』日期未定，先在主檔記成純文字，等她回覆再開待辦。」
- 原句：「這只表示無法從列項直接對上提案內容，不能推論未報價或未執行。」改後：「三張報價單沒有逐項對應的列項，是否報價或執行需要再查。」

具體的對話統計數據與設定檔寫法，我整理在文末的附錄中。

## 仰賴商業 AI 做 Agent，唯一的解法就是做好備援

我在課堂上也明確地說：這些模型商就是皮癢身子賤，輪流做死被唾棄的。如果公司未來要仰賴商業 AI 做 Agent，那就要做好備援，不然模型躺了公司也跟著躺了。

其實就意識到這兩家會輪流自作孽就好，平常心就好。

## 附錄：防禦式語氣調查數據與設定檔

近 30 天的對話統計（Codex 393 則、Claude 3136 則，篩選 150 字以上的訊息）：

| 指標 | Codex | Claude |
|---|---|---|
| 否定字總量（每 100 字） | 2.52 | 2.52 |
| 防禦句型（每千字）：不代表／不等於／不是…而是／不能直接／只能 | 1.80 | 1.13 |
| 「不代表／並不／不等於」（每千字） | 0.49 | 0.08 |
| 有防禦句型的訊息比例 | 48% | 36% |

兩邊否定字的量一樣多，差別在句型。Claude 說「不」是在描述事實；Codex 會多走一步，先替你擋掉誤讀，例如「X 不等於 Y，不能推論 Z」。

這不是設定同步造成的：給兩邊的指令密度差不多，全域層每千字禁止詞 Claude 1.61、Codex 1.92，能力模組是 1.39 對 1.38，各專案層幾乎相同，這點差距解釋不了 1.6 倍的句型差，更解釋不了 6 倍的「不代表」。同步機制只做原樣複製、連結或翻譯，沒有任何語氣處理。

真正的差別在語氣設定：Claude 有正面描述說明要什麼語氣；Codex 只有 personality = "pragmatic"（config.toml 第 3 行），其餘就是滿滿的禁止清單，沒有任何正面引導。另外「負向斷言必須驗證」這類規則（此點為推論，未經單獨實測），也可能讓 Codex 把「查不到」固定寫成防護句。

![終端機截圖：Claude 的調查結果與數據表，列出 Codex 與 Claude 的否定字總量、防禦句型每千字數量、「不代表」每千字數量與有防禦句型的訊息比例，並說明為什麼不是 harness 造成的](/blog/assets/posts/model-vendors-take-turns-failing/5-codex-defensive-stats.jpg)

建議做法：把語氣設定放在 ~/.codex/config.toml 頂層的 developer_instructions，不放共用專案說明檔（AGENTS.md），因為該檔是同步的翻譯目標，會被覆寫。設定草稿如下：

```toml
developer_instructions = """
用肯定句先說結論與下一步，再補必要的限制。
限制只寫一次，放在最相關的那句裡，不另開「不是…而是…」的澄清。
未驗證的事用「尚未驗證 X」陳述事實，不推論對方的誤解。
回報成果時說做了什麼、結果是什麼；沒做的事只在影響決策時提。
語氣像資深同事交接：簡短、確定、不替讀者預防誤讀。
"""
```
