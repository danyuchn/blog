你有沒有過這種經驗：為了讓 AI 助手更懂你的工作習慣，每次它犯錯，你就在設定裡多加一條規定；怕它不了解背景，又把過去的會議紀錄、踩坑教訓、SOP 筆記全部塞進它的固定說明裡。結果規定越寫越長，AI 卻開始漏掉你最在意的重點，反應越來越慢，額度還燒得飛快。

雖然說規矩立下了，路才能越走越寬；但是規矩適度拿掉，AI 的額度才能越來越省。

前陣子我跟一位學員訪談，他是一家公司的營運長（COO），已經把 Claude Code（Anthropic 推出的 AI 工作與寫程式助手）全面導入日常營運。他花了二十分鐘向我展示他的工作環境：串接了各種外部工具、寫了大量自訂的工作流程，還連上自己的 Obsidian 筆記庫，把過去所有的決策重點與錯誤教訓巨細靡遺地記下來。

但他很苦惱地跟我說，實際用起來，AI 沒辦法很好地配合調度這麼多工具。

我請他看了一下介面右下角的狀態，發現 AI 的上下文窗口（Context Window，也就是 AI 單次對話能記住與處理的記憶空間）已經被用到了 88%。往上翻對話紀錄，明明才剛聊沒幾句。一般來說，記憶空間用到 60% 就該整理壓縮了，剛開場就飆到 88% 顯然極不正常。

進一步檢查才發現，他強迫 AI 每次開口前都要先讀完所有他過去記下的「教訓」與知識庫文件，但這些背景資料大部分時候根本用不到；而且所有事情都硬塞在同一個對話視窗裡處理，沒有派分身去分擔。

## 為什麼規則塞越多，AI 反而抓不到重點？

很多人的直覺是把「規則的數量」當成「對 AI 的掌控程度」，以為把所有歷史教訓與業務規則全部寫進去，AI 就會更聽話。

事實正好相反。每次對話開頭固定塞給 AI 的每一條規則，都在競爭它的注意力。當設定裡充斥著故事背景、犯錯日期、人名範例，甚至前後互相矛盾的指示，它的記憶空間就會快速被塞爆。這就像你請了一位助理，卻要求他每做一件事之前都要把公司過去三年的會議紀錄重讀一遍——結果就是連貫性直線下滑，該呼叫工具的時候叫不出來，甚至連你最在意的那條核心規定都會漏掉。

當你管理這些固定規則（在 AI 開發裡常稱為 harness，也就是每次對話開啟時系統自動載入給 AI 的固定規則、行為準則與背景設定）的思維，從「加規則」轉向「減規則」的時候，通常代表兩件事：一是模型進化了，以前要耳提面命的事現在它自己就會；二是你進化了，知道怎麼用更精準的結構控制它。

## 明天就能試的做法：幫 AI 設定做減法的四個問題與「消融實驗」

如果你也覺得手上的 AI 助手越來越笨重，明天就可以試著幫你的固定提示詞或規則設定做一次大掃除。

首先，把規則裡所有的「故事背景」砍掉——當初為什麼犯錯、哪一天發生的、跟哪個客戶有關，這些敘事脈絡對 AI 來說都是雜訊，只留下硬性的行為約束就好。接著，用這四個問題逐一審視剩下的每一條規則：

1. **拿掉這條，AI 會不會犯錯？** 如果現在的模型不寫這條也不會做錯，就果斷拿掉。
2. **是不是只有特定任務或特定資料夾才會用到？** 如果是，就改成碰到那類工作時才讀取，不要每次開新對話都全部載入。
3. **是不是只跟某個特定工作流程有關？** 把它收進那個專屬的技能包（Skill，只在需要特定任務時才叫出來的操作說明書）裡，按需載入就好。
4. **這條是不是重要到絕對不允許違規？** 如果一犯錯就會出大事，不要只靠文字叮嚀，直接設成系統的自動攔截檢查（Hook）。

如果不知道怎麼挑哪些規則該砍，你可以試試我常做的「消融實驗」（Ablation Experiment，借用機器學習的方法：刻意拿掉系統裡的某些設定，觀察表現會不會變差，用來確認那些設定是不是真的有用）：

1. 請 AI 幫你檢查現有的固定規則，判斷哪些已經過時或重複可以砍掉。
2. **先留一份備份，然後直接砍掉。**
3. 照常工作一個禮拜，回來看看它的出錯率有沒有上升、每次對話的額度消耗有沒有下降。

這其實也是參考 Elon Musk 的極致減法哲學：砍掉以後如果沒出問題，就代表它本來就沒有存在的必要；如果真的漏掉了什麼，再把那條加回來就好。

除了清理固定規則，日常使用還有一個很容易被忽略的壞習慣：**千萬不要為了接續上一次的工作，就把前一次對話的完整歷史紀錄整包貼給 AI。** 原始對話紀錄裡有太多過程中的嘗試與無用資訊，整包倒進去只會瞬間污染新對話的記憶空間。需要跨對話交接工作時，請 AI 先把上一輪的重點提煉成簡短的摘要文件，或是依性質歸納進固定規則裡，讓新對話保持乾淨。

## 官方員工也在做一模一樣的事

好好笑，我寫完這套減法做法沒多久，發現自己真的是大預言家欸。

Anthropic 官方員工在我發文 6 小時後（他 10 小時前、我 16 小時前）發了一篇貼文，倡導的做法竟然跟我一模一樣：「提示詞先砍掉，有事再考慮加回來。」

![Anthropic 員工分享 Opus 5.5 指令精簡實驗的貼文截圖](/blog/assets/posts/harness-ablation-one-week/announcement.jpg)

那位員工在貼文裡提到，他們把 Claude Code 內建的系統提示詞刪掉了 80% 以上，結果寫程式的評測表現沒有任何可測量的下降。他也建議大家在像 Opus 5.5 這樣的新模型推出時，對自己的指令做同樣的三步循環：

1. 刪掉一部分舊規則
2. 觀察模型漏掉了什麼
3. 只加回真正需要的那些，而且每換一代新模型就重複一次

## 我自己的三次「減肥」實測：少掉三成規則，AI 反而更快更穩

這套減法我自己在半年內完整做過三輪，每次都有具體的數據變化。

**第一輪是規則大掃除（瘦身 36%）。** 那天深夜剛好拿到 Opus 4.8 新模型、週額度也重置，我做的第一件事不是派新工作給它，是請 AI 組一隊分身（Subagent，由主 AI 派出去平行處理子任務的獨立小助手，用完就收，不會佔用主對話的記憶空間）幫我的設定檔徹底體檢，把重複、互相衝突的條文和故事背景全砍了。

整理完之後，我的固定規則總行數直接減少了 36%。很有感的是，後來用新模型時完全不覺得特別耗額度，回應速度甚至比之前還快——因為我幫它留了一個乾淨的記憶空間，給它的都是不衝突、不重複的精煉規範。

**第二輪是半年後的技能包大合併（從 58 個砍到 40 個）。** 規則變乾淨後，我發現自己累積的專屬技能包（Skills）也開始膨脹。於是半年後我做了第二次更大規模的整理：把全域的 58 個技能包與各專案裡的 66 個全部盤點一遍，直接下架 12 個不常用的，再把主題相近的合併（例如把 6 本商業書的獨立筆記合併成單一入口，把中英文潤稿、不同語氣的信件改寫各自合一），一口氣從 58 個縮減到 40 個。

**第三輪是為期一週的消融實驗對照。** 在 10/21 那天，我再做了一次設定改版，目標很單純：讓每場對話開頭塞給 AI 的固定說明更少、讓它自己判斷什麼時候不用停下來問我、並把雜事外包給其他 AI 工具（像是 Codex 等）。改之前我先量了一份基準數字，並在 10/24 額外拿掉 12 組常駐規則，約好一週後回來對帳。

![改設定前後一週的數據回報截圖](/blog/assets/posts/harness-ablation-one-week/1-one-week-results.jpg)

滿一週跑出來的實際結果非常清楚：

1. **每次對話的開場負擔少了兩成**（每場開頭大約少載入 1.8 萬個字元單位）。
2. **單一動作的成本變便宜，總花費沒變**。雖然單場對話花的錢多了兩成，但那是因為記憶空間變乾淨後，單場能交代它做完的事情變多了，平均每做一個動作反而更省。
3. **出錯率沒有上升**。真正的失誤少了很多，而新加的自動攔截規則（Hook）成功擋下了幾次違規，兩邊剛好抵銷。被系統攔下來是刻意設計的安全網，不算壞事。
4. **外包給其他 AI 工具的成功率從 75% 升到 94%**（其中外包給 Codex 的部分最弱，約七成）。因為主規則理順了，派工給其他工具時指令也更清楚。

無論你平常習慣用的是哪一款 AI 工具，模型的記憶空間再大，也不代表可以隨意堆放雜物。在把繁重的工作丟給 AI 之前，先幫它把環境裡過時的規矩清一清，留一套不衝突、不囉嗦的工作說明，它才能真正穩定地幫你省時間。

## 給想自己動手的人：技術實作細節與指令參考

如果你已經在使用 Claude Code 或類似的開發工具，想直接在自己的環境裡重現上面提到的診斷、清理與消融實驗，這裡整理了具體的操作指令與底層機制。

### 1. 診斷上下文空間與過時規則的指令

- **檢查記憶空間佔用（`/context`）**：在 Claude Code 中輸入 `/context`，可以直接查看目前對話中，系統內建設定（`CLAUDE.md`、rules、skills、hooks、memory）與外部載入文件各自佔用了多少上下文比例。當上下文使用量達到 60% 時建議主動觸發壓縮（auto compact 會自動摘除歷史對話中無用的 tool call、output 與 flag；這也是為什麼千萬不要把前一次對話的原始 session history JSON 直接餵給新對話）。
- **官方提示詞健檢指令**：不知道哪些舊規則該砍時，可以使用 `/claude-api prompt-audit`，或如 Anthropic 員工提到的 `/doctor prompt-audit`，系統會協助標記出那些針對舊模型寫的過時規則。
- **直接請 AI 優化設定的萬用指令**：
  > 「上網看看官方推薦 5.5 harness 要怎麼寫
  > 然後回來幫我優化所有現行的 harness
  > 優先考慮簡化、去重、避免衝突、按需載入
  > 並且加上 hook 避免未來寫入格式飄移」

### 2. 派一隊 Subagent 重整 Harness 的六步流程與 Prompt

在進行第一輪瘦身 36% 時，我是切換到計畫模式（Plan Mode），直接下這段指令讓模型自己組隊體檢：

> 請你派儘可能多的 subagent，去調查我的 user-level、跟每個 project-level 的 `CLAUDE.md` / rules / hooks / memory / skills，找重複跟衝突，精簡常態注入，但以 harness 行為不變為最高原則。砍敘事脈絡（例子、人名、犯錯日期、範例），只留模型約束。

模型規劃並執行的六步清理流程如下（每完成一步，都會派出一個不繼承任何歷史上下文的全新 subagent 獨立驗收，確認無誤才推進）：

1. **平行掃描**：派出多個探索 subagent，分別掃描全域（user-level）與各專案（project-level）的設定檔並對照官方最佳實踐，避免單一上下文被塞爆而出現調查失誤。
2. **砍除敘事脈絡**：刪除每個文件中的人名、犯錯歷史與背景說明，只留硬性約束，並拆解為細粒度待辦清單防止漏檔。
3. **精煉 Skill 觸發描述**：針對每個 Skill 的 YAML `description` 進行精簡（控制在 ≤200 字元並補齊口語觸發詞），確保按需觸發精準不冗餘。
4. **改寫 `@import` 引用**：檢查設定檔中帶有 `@import` 的引用語法，將不需常態載入的文檔改為純檔案路徑，避免每次啟動都被強制展開。
5. **四道關卡分層過濾**：依序檢查「拿掉會不會犯錯（不會就刪）→ 是否僅特定路徑用到（下放為路徑限定 rules）→ 是否僅特定流程用到（併入對應 Skill）→ 是否絕不允許違規（改寫為硬性攔截的 Hook）」。在第二輪將全域 Skills 從 58 個砍到 40 個時，也是由兩個 Sonnet subagent 先盤點全域 58 個與專案 66 個 Skills，再將不適合做為獨立 Skill 的項目降轉為常駐 `rules/common/` 或 `memory` 裡的 reference，下架的移入 `~/.claude/skills/_archived/`，最後跑完 YAML 格式驗證與跨檔案交叉引用修正。
6. **語意向量比對去重**：引入文字嵌入模型（`gemini-embedding`）為每一條約束建立語意向量，透過相似度計算找出跨檔案中意思重疊或互相抵觸的條文，徹底消除重複與衝突注入。

此外，如果你同時在 Claude Code 與 Codex（或 `AGENTS.md` 體系）之間切換工作，建議透過同步腳本定期同步兩側的規則與設定；消融實驗滿一週後，也可以透過掃描本地對話紀錄的 `.jsonl` 檔案，定量比對任務出錯率與平均每任務成本的變化。
