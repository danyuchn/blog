你一定遇過這種兩難：訂了最頂級的 AI 方案，用最聰明的模型處理工作時，它真的懂你在說什麼，連藏在細節裡的規定都不會漏；但沒聊幾句，系統就跳出「額度已達上限」。等你被迫切回一般模型，它又開始忘東忘西，明明交代過三次「不要這樣寫」，下一段還是照犯。

問題通常不是一般模型太笨，而是我們把最聰明的模型用錯了地方。

大多數人拿到最高階的 AI，還是習慣拿它來做日常瑣事——改一封信、順一段稿、整理一份零散的筆記。這樣用，就像請一位鐘點費極高的資深顧問，卻叫他坐在旁邊幫你打字一樣，額度燒光了，下次換一位新助理進來，你還是得從頭教起。

真正划算的用法，是反過來：**別叫最貴的模型幫你做日常小事，而是請它幫你「寫規矩」。**

我把這套做法叫做 **Skill Distillation（技能蒸餾——把高階模型的判斷力，提煉成一般模型也能重複照做的標準工作規範）**。不管你是備課出題的老師、審核報告的主管，還是每天要產出專業文件的顧問，明天打開 AI 就能直接用上。

## 為什麼你交代了十條規則，AI 總是會漏掉兩條？

我們平常跟 AI 合作，最常卡在「經驗沒有留下來」。

你在對話框裡糾正它十次，它終於改對了；但開一個新對話，或者換成速度較快、比較便宜的模型，之前的教訓就全部歸零。因為一般模型擅長的是「照著明確清楚的步驟執行」，卻不擅長在混亂的舊資料與模糊的指令之間自己抓重點、解衝突。

最高階模型的價值就在這裡。它的推理與全局判斷力最強，最適合拿來做兩件事：
1. **看懂全局與找出矛盾**：把你手邊零散的舊檔案、過去踩過的坑一次讀完，找出哪裡規則互相打架、哪裡沒講清楚。
2. **寫出誰都能照做的操作手冊**：把那些原本只存在你腦子裡、或是要靠高階模型才想得到的判斷標準，寫成白紙黑字的檢查表與步驟。

只要讓最高階的模型把這份「工作手冊」寫好，接下來每天重複的日常執行，交給便宜、額度充裕的一般模型照著做，品質就能穩穩守住。

## 明天就能試的「技能蒸餾」四步驟

下次當你要啟動一個重要工作，或是手上有個高階模型的限時額度時，不要直接叫它產出最終成品，試著照這四個步驟走：

![圖卡：Skill Distillation 怎麼做](/blog/assets/posts/fable-5-return-skill-distillation/card-2-skill-distillation.jpg)

### 第一步：先讀不先寫
把你手邊跟這項工作有關的既有資料——過去的範本、常犯錯誤紀錄、評分或審核標準、背景說明文件——全部餵給最高階的模型。這一步只有一個要求：**先看懂，不准動手改成品。**

### 第二步：請它反問你 5 個「資料裡看不出來」的問題
資料讀完後，別急著叫它寫規範。請它根據剛才看過的所有內容，挑出 **5 個現有文件裡沒寫清楚、或者規則彼此衝突、必須由你本人拍板的問題**來問你。這一步非常關鍵，能幫你把平常自己都沒意識到的模糊地帶一次補齊。

### 第三步：扮演「即將退休的資深總設計師」，只寫工作手冊
回答完那 5 個問題後，請它扮演一位「即將退休、要把畢生判斷力交接給後輩的資深總設計師（Principal Architect）」。要求它把判斷標準寫成耐用、可重複執行的標準工作規範與操作手冊，並且**嚴格限制它：只准寫工作規範，不准直接修改你的成品**。寫完後，再請它針對這份規範自己跑三輪檢查。

![圖卡：Skill Distillation 的 Prompt 骨架](/blog/assets/posts/fable-5-return-skill-distillation/card-4-prompt-skeleton.jpg)

### 第四步：日常執行交給平價模型，人只管頭尾
規矩定好之後，你的分工就變得很清楚：

* **最高階模型當「總設計師（Architect）」**：只在開頭跟關鍵時刻出場，負責制定規格、審查架構、分析為什麼上次會失敗、彙整研究，以及把判斷寫成工作規範。
* **一般主力模型當「執行者（Executor）」**：負責照著寫好的計畫與規範動手做、日常產出、小修小補、反覆修改。而且每次只派給它範圍明確的小任務，避免單一對話塞進太多雜訊而開始恍神。
* **你（人類）負責三個決策點**：決定什麼時候值得動用最貴的模型、一次給齊完整的需求背景（Brief）、最後驗收成品。

這套分工有兩條鐵則：**完整需求一次給齊；先審核工作規格，再讓 AI 動手做成品。**

![圖卡：Fable 當 Architect，Opus/Sonnet 當 Executor](/blog/assets/posts/fable-5-return-skill-distillation/card-3-architect-executor.jpg)

## 真實驗證：從整理工作區到寫出兩篇學術論文

這套做法不是紙上談兵，而是我在 Anthropic 限時一週開放最高階模型 Fable 5 時，自己與身邊教授朋友實測出來的結果。

### 案例一：用一週限時額度，幫自己的工作資料夾立好規矩
當 Fable 5 限時回歸一週、且只佔每週使用上限的一半時，我第一天就把它的額度用滿了——但我沒有拿它來寫日常小東西。

我交給它的核心任務，是全面檢查我工作資料夾裡的檔案結構與 AI 工作規範：把過舊的內容封存、讓主要設定檔保持精簡，並把不同文件裡互相衝突的規則化解掉。為了省下 Fable 5 的寶貴算力，我要求它本人只做「規劃」與「最後驗證」，真正動手搬移、修改各個小檔案的執行工作，全部派給較輕量的 Sonnet 5 分頭處理。

結果一週結束後，就算限時額度沒了，那套被高階模型整理得乾乾淨淨的工作規範依然留在資料夾裡，之後每天讓日常模型照著跑，完全不會走樣。

### 案例二：教授朋友用三份文件，從頭寫出兩篇準備投稿的論文
更直接的壓力測試，來自我的教授朋友。學術論文對格式、推導邏輯與寫作禁令的要求極高，只要漏掉一條規則，整段推論就可能作廢。

趁著 Fable 5 還能用訂閱額度跑（之後改走按量計費的 API，價格高到堪比台灣國旅），我請教授朋友把他正在寫的論文題目與資料夾拿來測試能力邊界。

他完全從頭開始，起手只有三份文件：
1. **研究主題提案（Proposal）**：這篇論文要解決什麼問題。
2. **研究與寫作指令（Prompt）**：規範 AI 怎麼做研究、怎麼寫論文的標準流程。
3. **避坑工作流（Workflow）**：這是最關鍵的一份——他把過去寫論文時 AI 做錯的大量教訓，全部寫成「絕對不能犯」的負面約束清單。

同樣把這三份文件餵給不同的主流模型，照教授朋友實測後的原話：

> 「Opus 會漏幾條規則，Fable 完全不漏、一次過，Gemini 跟 GPT 是完全沒有在鳥的。」

教授朋友早上借用我的帳號測試，他說 Fable 5 寫出來的數學證明既自然又簡潔優雅，而且一次過關、完全不會錯。他就這樣從無到有寫出了兩篇論文，已經準備投出去；如果換算成按量計費的 API 成本，兩篇大約是 200 美元。

那次為了測極限，我們故意把所有協作分身都開到滿、全部用最貴的 Fable 5。但事後我們一起覆盤，最划算的黃金組合其實不必全程燒最貴的模型：**只有最前面的規劃、架構設計與最後驗收用最高階的 Fable 5，中間撰寫初稿、跑實驗與畫圖，分別交給不同專長的平價或主力模型接手。** 教授朋友算了算說，就算未來要用 API，平均 100 美元能寫出一篇守住所有嚴格規則的論文，其實非常划算。

下次拿到最強的 AI，先別急著叫它幫你趕眼前的雜事。花一點額度，請它讀完你的過去經驗、問你 5 個關鍵問題、幫你寫下一份標準作業流程——這才是額度用完之後，每天還能幫你省下大把時間的資產。

## 進階技術專區：給想在 Claude Code 實作的人

如果你有在使用 Claude Code 或多模型工作流，以下是這次實測的完整技術設定與操作細節：

![Anthropic 官方公告：Fable 5 與 Mythos 5 出口管制解除，7/1 起回歸](/blog/assets/posts/fable-5-return-skill-distillation/announcement.jpg)

### 1. Fable 5 官方開放規格與額度計算
根據 Anthropic 官方公告，截至 6/30，Fable 5（即 Mythos 的護欄版本）與 Mythos 5 的出口管制解除；自 7/1（週三）起，Fable 5 在 Claude 全平台（Claude.ai、Claude Code、Claude Cowork）開放。在 Pro、Max、Team 與部分 Enterprise 方案中，7/7 前 Fable 5 會計入每週使用量上限的最高 50% 以內，7/7 之後則改由按量計費的使用額度（API / usage credits）提供。

### 2. Project-level Harness 優化與 Subagent 分工
在 Claude Code 專案中，我請 Fable 5 根據官方文檔優化專案層級的 `harness`（即控制 AI 行為的整套配置檔，包含 `SKILL`、`memory`、`rules` 與 `claude.md`），將過期內容歸檔（archive）、維持主檔精簡並消解規則衝突。這套做法也參考了 Reddit `r/ClaudeAI` 版上關於「讓 Fable 5 寫 skills」的討論。

執行時的算力保護機制：
* **Main Agent（Fable 5）**：只做規劃（planning）與驗證（verification）。
* **Subagents（Sonnet 5）**：由主代理派發給 Sonnet 5 的子代理（subagent）執行單一、範圍明確的小任務，確保每個子代理的 `context window`（對話上下文視窗）保持乾淨，並為後續接手的 Opus / Sonnet 打好專案規矩。

### 3. Skill Distillation 的工程版執行流程與 Prompt 約束
在程式碼倉庫（repo）中執行 Skill Distillation 的具體步驟：
1. **全庫唯讀掃描**：要求 Fable 5 先讀 repo 不先寫——把 `README`、測試、`CI`、`docs`、`git history`、失敗紀錄全部讀過。
2. **釐清隱性知識**：請模型提出 5 個光看 repo 看不出來的架構或業務問題。
3. **產出 Durable Skills 並跑三輪 Review**：Prompt 骨架設定為「請高階模型扮演一個即將退休的 principal architect，把專案判斷轉成 durable skills，而且**只准寫 `skill` / `runbook`，不准動 `source code`**」，產出後執行三輪 review。
4. **Architect vs. Executor 職責切分**：Fable 擔任 architect（負責 `spec`、架構審查、失敗分析、研究彙整）；Opus / Sonnet 擔任 executor（照 `plan` 實作、日常 coding、小修小補、反覆迭代）；人類負責決定何時動用 Fable、一次給齊大 `brief`、先審 `spec` 再寫 `code`、最後驗收輸出。

### 4. 學術論文實驗的多模型路由配置
教授朋友的測試題目為 `federated learning`（聯邦學習），輸入 repo 僅包含三份起手文檔：`proposal`（研究主題提案）、`prompt`（研究與論文撰寫規範）、`workflow`（將過往寫作錯誤整理成的負面約束）。

* **極限測試配置**：所有 subagent 全開 Fable 5，從零產出兩篇論文，折合 API 成本約 200 USD。
* **事後收斂的最佳路由配置**：
  * `plan` / `architecture` / `final verification`：Fable 5
  * 撰寫 `transcript`（論文初稿）：Opus 4.8
  * 跑實驗與寫 `code`：composer 2.5
  * 繪製圖表：gpt-image-2
* **推理強度（Effort）參數備忘**：Reddit 社群有討論指出 `effort` 開 `high` 仍不夠，開到 `xhigh` 才有明顯增益，這點可作為後續實測調參的參考。
