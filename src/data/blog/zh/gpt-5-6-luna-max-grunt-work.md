很多人挑選 AI 模型時，容易「全方位」嫌棄參數較小或定位平價的模型。但在真實世界的工作流裡，常常需要面對枯燥、機械的「雜活」：去沒有公開 API 又愛擋爬蟲的網站抓報表、在介面複雜的航空系統上反覆切換幾十個日期找機位、手動對照試算表把上百位客戶的資料逐一貼到後台側邊欄。

有時候只是一次性想要爬取資料，不想硬幹冒被封鎖的風險，也不想為此花錢跟第三方買資料。會在那裡「全方位」嫌棄某某模型的人，其實就是想像力太過狹隘，想要用拉踩某些模型顯現自己很懂。每個模型都有他適用的 use case，端看你有沒有想像力。在我眼裡，就連 Gemini 都有它的一席之地。解決雜活的核心，在於建立分工架構：讓平價模型包辦瀏覽器與電腦雜活，由高階模型負責最後審核、把目標做完。

## 雜活的真正痛點：為什麼旗艦模型不是最佳解

真實工作流中的雜活通常具備幾個特徵：沒有官方 API、介面充斥嚴格的反爬機制、流程包含大量重試與等待，且極度消耗 token。

過往面對這類無 API 又愛擋爬的網站，通常有兩種選擇：要嘛讓 AI 下載各種套件或腳本跟網站的反爬機制「仙拼仙」，冒被封鎖的風險；要嘛花錢向第三方 API 購買資料。但很多時候只是臨時性、低頻率的需求，既不想硬幹冒風險，也不想為此花錢買資料。

平價模型在這種場景下是天然的解法。以當時實測的 GPT-5.6 Luna Max 為例，它最厲害的就是做土法煉鋼的瀏覽器爬蟲，直接操縱真實的桌面瀏覽器，token、指紋、速度、頻率全部都跟人類相仿。我目前天天爬也沒有被 403。放著跑一整個晚上，醒來才掉 5% 血量，任務順利完成。

在一個實際測試中，我分派了跨平台抓取財務報表的任務：讓代理直接操控真實瀏覽器，前往各家銀行與收款平台（由我人工協助登入後），把缺漏的報表下載回來。這項操作故意不走 API、MCP 或命令列工具，純靠瀏覽器點擊與畫面確認。

如下方終端機截圖所示，代理下達目標指令後，在 22 分鐘內（標示 Worked for 21m 49s）圓滿完成，順利下載四份財務報表並核對格式與日期。當時連同另一個已跑了一小時、還在進行中的任務，目前看週額度才耗 1%，用 token 換算 API 價格大概 3.14 美元。

![終端機顯示 agent 完成後回報四份財務報表已下載並核對格式與日期，底部標示 Worked for 21m 49s](/blog/assets/posts/gpt-5-6-luna-max-grunt-work/1-luna-max-goal.jpg)

這麼高的性價比，已經不是跟 A＼比的問題了。我覺得 DeepSeek 的用戶可能都會被拉走，畢竟論 token efficiency、論 agent 能力、論 computer／browser use，DeepSeek 應該也很難跟 GPT-5.6 打。我願稱 GPT-5.6 Luna 是新一代的雜活之王。

## 瀏覽器爬蟲與介面操控：廉價模型的天然主場

機械性的資訊比對與抓取，是平價代理最能發揮價值的場景。主要應用包括以下幾類：

第一是社群平台的輿論觀測。爬社群網站文章時，理由是不想冒風險對幹反爬、偶爾查頻率不高，不想特意買第三方 API 的資料。

第二是航空公司的里程票機位。用過 ANA 的人才知道他們的里程票系統之爛、規則之複雜，而且完全沒有 API 能做這件事。查詢機位需要機械性地切換幾十個天數組合，看一眼有沒有位置，抄寫空位資料與航班資訊給我做最終決定。謝謝 GPT 5.6 Luna Max，前天才幫我刷到曼谷東京商務艙兩位。

如下圖所示，終端機正持續逐點測試日期組合，右側瀏覽器則同步展開 ANA 特典預約頁面的日曆選單逐一核對：

![終端機正在逐點測試 BKK-KIX 各日期，右側 Chrome 開著 ANA 日文特典預約頁面的日曆選單，上方顯示 ChatGPT started debugging this browser 提示條](/blog/assets/posts/gpt-5-6-luna-max-grunt-work/2-ana-award-seats.jpg)

另外，敬告國泰航空：雖然你們的人機驗證很先進，但 GPT Luna max 還是在我眼前一個一個的破解了。如下圖所示，在國泰航空網站的圖片驗證中，準確勾選出所有早餐吃的食物：

![國泰航空網站的圖片人機驗證，題目要求選出所有早餐吃的東西，其中幾格已被勾選](/blog/assets/posts/gpt-5-6-luna-max-grunt-work/cathay-captcha.jpg)

第三是住宿平台比價與最低價格保障申請。平價模型已經足夠理解最低價格保障的規則與條款，能自動比對不同訂房平台，甚至協助申請退款。

第四是遠端跨通訊軟體的文件中繼。人在外面時，用手機遙控告訴代理：幫我打開 LINE 或 Messenger，把對方要的文件下載下來，叫 Sol／Terra 處理後，由 Luna 去 LINE 發還給他——目前已經用這個方式遠端完成不少。同理 104 篩選職缺、一大堆平台查飯店比價，都是 Luna Max 最愛用的場景。關於這些操作的實際錄影，我在影片中做過示範（EP.34 <https://youtu.be/8Sxw1Mdcl8Q>）。

## 跨系統資料搬運與長任務實戰

除了單向的網頁爬取，另一類耗費大量人力的雜活是跨系統的資料搬運與格式同步。

有誰跟我一樣，也很討厭管理 LINE 官方帳號後台的這個側邊欄？客戶的報名資料在 Google Drive 裡的表單，客戶的資料夾也散落在 Google Drive 各處。過去我都是一個一個看，然後手動上標籤、在記事本核對。

如下圖所示，這類工作步驟固定、需要核對的欄位瑣碎，純粹折磨體力：

![LINE 官方帳號後台的客戶側邊欄：方案標籤、負責人員與記事本，記事本裡寫著方案到期日與 Google Drive 資料夾（客戶資訊已遮蔽）](/blog/assets/posts/gpt-5-6-luna-max-grunt-work/line-oa-sidebar.jpg)

後來我讓當時的 GPT-6 Luna Max 去做這種雜活，100 多個客戶約一個小時左右完成標註同步，才花 20 美元 5 小時額度的 5%、週額度的 1%。省是真的省，慢是唯一的缺點，做出來我讓 Opus 快速檢查一遍也沒有漏。

同樣的模式也可以套用在長時間的環境同步任務上。例如讓代理把 Claude Code 那邊的 harness 同步到 Codex 這邊來（已有 SKILL），下達 `/goal` 後跑了一個小時現在還在有序進行中。

在影音後製領域也是一樣。秉持「哪家模型都必有大用」的原則，我曾嘗試全程用平價模型搭配 HyperFrames，做出一支 20 分鐘的長版影片；在專業剪輯軟體中，Davinci Resolve Studio 配控制協議給平價模型操控，就是新世界影片後製的神，做這種雜活真的是世界第一名。

## 高低搭配：衝鋒幹活與規格審核的雙層架構

在長片製作與後製實驗中，如果搭配一套規格非常固定的流水線，那就還算可以；但 Luna Max 寫好的影片規格會在某些幕景中有飄移，需要修正。同樣的毛病在別的地方也看得到：LUNA 寫好規格還是很容易會飄，他真的只適合收集資料的任務，也就是機械性的瀏覽器操作。

做完之後我的心得是：下次搭配一個高階模型來做最後審核，整體流程會順利得多。這正是建立「雙層分工架構」的核心：
- 廉價端模型：負責衝鋒幹活，包辦耗時、重複、機械性的瀏覽器點擊、資料收集與素材搬運。
- 高階端模型：負責最後審核，死死咬著目標把它做完。

我都跟別人說，GPT 5.6 Sol 是瘋狗。當你給他 /狗死 下去（我還會順便放音樂，LISA 的「狗死～狗死～」），他就會死死咬著目標把它做完，不做完不罷休。

而雜活的第一優選則是 5.6 Terra high，操縱瀏覽器跟電腦仍然非常準，連複雜的里程查票任務都能搞定。重點是額度省之又省，可以把 Sol 用在更重要的事情之上。用過 GPT 跟 Claude 兩者的 computer control MCP 之後，任何人都會驚訝兩者的差異：一家操作非常絲滑流暢且檢查細心，另外一家會亂搶滑鼠跟輕易放棄操作。

模型也不是只比聰不聰明，還要看資料入口。例如 X 或 Threads 這類社群網站，有的環境直接發送網路請求常被阻擋，必須繞瀏覽器；Gemini 卻能直接讀取。Reddit 對某些工具特別不友善，另一些環境反而順暢。掌握不同工具的資料入口特質，才能讓雜活走得通。

## 雜活選型判準與操作邊界

面對日常的自動化任務，可以透過以下幾項具體判準來決定模型的配置：

第一，凡是沒有 API、會擋爬蟲、傳統很耗費 token 的任務，靠瀏覽器或電腦操控，Luna 是不二選擇；額度省之又省，可以把高階模型用在更重要的事情之上。

第二，LUNA 適合收集資料與機械性的瀏覽器操作，但寫好規格還是容易會飄。如果在任務中遇到規格飄移，可以搭配一套規格非常固定的流水線，或者搭配高階模型來做最後審核。

第三，不要「全方位」嫌棄某某模型，每個模型都有它適用的 use case。模型不是只比聰不聰明，還要看資料入口與介面操控，端看你有沒有想像力把它們放在合適的位置。
