你一定遇過這種狀況：剛開始跟 AI 合作一件事時，它又快又準，簡直像撿到寶；但隨著事情變複雜、對話變長，它卻突然開始忘東忘西，甚至自作主張把原本寫好的東西改壞。

這時候，我們直覺的反應通常是繼續打字罵它、貼上更長的說明去糾正它。但越糾正，對話就越混亂，最後只會得出一個結論：「AI 真的很不穩定，有時候很神，有時候很蠢。」

我以前也這樣覺得。直到後來在網路論壇 Reddit 上看到一篇獲得 778 個讚、引起 157 則留言熱烈討論的貼文，我才意識到：**問題根本不是 AI 不穩定，而是我們一直卡在同一個用法的天花板，沒有升上去。**

那篇貼文的作者（u/DevMoses）原本是在討論 Claude Code（一款能直接讀寫電腦資料夾與檔案的 AI 工具），他把人們使用 AI 的方式整理成五個成熟度階段。底下大量網友留言驚呼「找到答案了」。

這套框架最迷人的地方在於它的核心邏輯：**「你不是自己決定升級的，你是撞到天花板才被迫升級的。」** 每一層新做法之所以存在，都是因為上一層的做法在某個時間點開始壞掉了。

雖然原作者是用寫程式當例子，但這五個階段的撞牆過程，對平常只用 AI 聊天寫教案的老師、審報告的主管、或是處理日常庶務的專業工作者來說，道理完全相通。你不需要把五層全部走完，只要看懂這個升級邏輯，明天就能徹底改變你跟 AI 合作的方式。

---

## 第一層：只靠聊天交辦（Raw Prompting）
**你在做的事**：打開對話框，直接打字告訴 AI 你現在要什麼。

這是所有人最熟悉的第一步。事情很單純的時候，這樣做非常有效。

**什麼時候會壞掉**：當你的工作變大、累積了越來越多慣例之後。你會發現 AI 開始忘記你上次提過的格式、每次給出來的做法都不太一致。你被迫在每一次開新對話時，重新把背景跟要求複製貼上一遍。當你覺得「怎麼每次都要重講」的時候，就是撞到第一層的天花板了。

## 第二層：給它一張「總規則小抄」
**你在做的事**：不再每次重講，而是寫好一份固定的背景說明與規矩（包含你的工作背景、命名與格式規範、絕對禁止做的事），讓 AI 每次開工前都先讀過。

這就像是替新來的助理準備一頁「辦公室生存守則」。剛換到這一層時，你會覺得豁然開朗，AI 突然變得超懂你。

**什麼時候會壞掉**：這是最多人產生共鳴的痛點。討論串裡大量的人都在說同一件事：**「感覺找到答案了，然後某個瞬間它就不管用了。」**

為什麼？因為當你發現這張小抄好用，就會忍不住把所有吃過的虧、所有細節規定全部塞進去。當這份總規則寫得太長（原作者發現超過大約 100 行之後），或是單次對話拖得太久，AI 遵守規則的程度就會開始下降，對話品質也跟著衰退。

原作者後來把自己的總規則從 145 行縮到 77 行，失控的狀況才終於改善。**總規則不是越長越好，塞太滿反而記不住。**

## 第三層：把長規矩拆成「單項工作手冊」（Skills）
**你在做的事**：既然一張總規則塞不下所有事，那就把特定任務的標準作業流程（SOP）拆開，寫成一份份獨立的「工作手冊」。

總規則裡只留最核心的大原則；至於個別任務怎麼做，各自寫成獨立的小手冊，需要做那件事的時候才按需載入給 AI 看。

如果你平常只用網頁版聊天、不想開終端機碰複雜的工具，你可以直接用聊天工具內建的「自訂指令（Custom Instructions）」來近似這個效果。

**什麼時候會壞掉**：有了手冊，AI 確實會照著步驟做。但問題是，**沒有人幫你自動檢查它做出來的品質**。你仍然是唯一的品管員（QA），當要處理的事情一多，光靠自己盯著檢查就會撐不住。

## 第四層：加上「交件前的強制檢查關卡」
**你在做的事**：不再只靠 AI 的自覺，而是設立品質檢查流程。每次它改完東西、或準備完成任務之前，強制先過一次品質門檻。

在進階工具裡，這可以設定成自動觸發的檢查腳本；但就算你只是用一般的對話介面，明天也可以立刻借用這個概念：**直接在你的指令（Prompt）裡內建一道「手動檢查流程」**，要求 AI 在交出最終答案前，先照流程核對一遍。

**什麼時候會壞掉**：即便加上了檢查關卡，你面對的終究還是「單一一個 AI 助理、在單一一個對話視窗裡工作」。所有的資料和修改紀錄都塞在同一個對話裡，一旦任務龐大到超過它單次對話能記住的容量上限，它還是會撐不住。

## 第五層：多工調度（Orchestration）——給專業開發者的領域
當單一助理撐不住，第五層的做法就是「同時派出一群 AI 助理平行分工」，各自有獨立的工作區、跨對話管理進度，並透過協調機制防止大家同時改到同一個檔案而打架。

老實說，這一層目前幾乎只有寫程式的開發者有辦法用。而且原作者也特別警告：**「跳級是災難。」** 每一層的基礎設施都是下一層的前提。如果你從第二層直接跳到第五層，還沒把規則、工作手冊與檢查關卡建好就想叫一群 AI 同時做事，等著出亂子。

甚至在討論串底下，還有網友提出了更進階的「第六層」：讓 AI 替你打造客製化的 AI 工作流，讓系統自我改善——在每次對話結束時自動提取你的行為模式，在夜間整合成新的工作手冊，測試通過後自動升級。這雖然已經超出大多數人的需求，但方向是對的：理想狀態是系統知道自己哪裡不夠好，然後自己補起來。

## 我自己實際走過這一遭的體會

看懂這五個階段後，我回頭盤點了自己目前的工作方式：我現在大概就处在第三層和第四層之間。

我的「總規則」已經有了，「單項工作手冊」也架起來了，但「自動檢查關卡」目前只開了一部分。至於第五層的多工調度，我也實際試過幾次，結果每次都在某個我沒預料到的地方壞掉。

但這套框架給了我一個很清楚的座標。現在當 AI 又開始犯傻時，我至少知道那不是工具本身不穩定，而是我的基礎設施還不夠。

### 明天上班，你可以這樣試：
這個框架對非開發者最大的用處，不是要你把五層全走完，而是讓你知道該怎麼對症下藥。明天打開 AI 時，試著觀察自己卡在哪一層：

1. **如果你還在每次重打一樣的叮嚀（卡在 L1）**：把你最常交代的背景、規範與禁止事項寫成一份固定的「總規則」，並把長度控制在 100 行以內（就像原作者從 145 行縮到 77 行那樣），別讓它變成什麼都塞的大雜燴。
2. **如果你已經有固定規則，但 AI 最近常無視它（卡在 L2）**：檢查那份規則是不是已經超過大約 100 行了。把特定任務才用得到的 SOP 抽出來，放進自訂指令（Custom Instructions）或獨立的「單項工作手冊」，需要時再載入。
3. **如果你總是在當唯一的品管員幫 AI 挑錯（卡在 L3）**：在你的對話指令裡內建一套「手動檢查流程」，讓 AI 在完成任務前先跑過這道品質門檻。

當 AI 開始犯蠢，下一步要加的從來不是更多的聊天，而是更好的結構。

## 給想自己動手設定的人：Claude Code 技術細節與進階數據

如果你本身有在使用 Claude Code 或想實際把這五層架設起來，以下是原貼文（作者 u/DevMoses）中的具體技術配置、限制與實測數據：

* **L1（Raw Prompting）技術痛點**：專案變大後，Agent 會開始忘記慣例，並引入不一致的 pattern。
* **L2（`CLAUDE.md`）配置與行數限制**：在專案根目錄放置 context 檔 `CLAUDE.md`，寫入 tech stack、命名規範與禁止事項。
  * **限制與企業級例外**：超過大約 100 行後合規度會下降，且長 session 品質也會跟著衰退（作者將自己的 `CLAUDE.md` 從 145 行縮到 77 行，情況才改善）。不過也有幾個數十萬行程式碼的企業用戶表示他們的 `CLAUDE.md` 從未失效，可能跟使用方式和 repo 結構有關。
* **L3（Skills）目錄與 Token 成本**：在 `.claude/skills/` 目錄下放置 SOP 檔案，按需載入，教 Agent 怎麼做特定任務。
  * **隱藏成本**：Skills 不是零消耗。檔案開頭的 Frontmatter（寫在檔案最上方用來標記手冊資訊的區塊）仍有少量 token 發現成本，不是完全免費的上下文。
* **L4（Hooks）生命週期腳本**：利用 Hooks（在特定時間點自動執行的生命週期腳本）在每次編輯後自動跑 typecheck、完成前設品質門檻、以及在 session 開始時載入 context。瓶頸在於仍是單一 agent、單一 session，一旦超過 context window（AI 單次對話能容納的記憶視窗）容量就撐不住。
* **L5（Orchestration）平行架構與實測數據**：透過平行 agents + isolated worktrees（隔離的工作目錄副本，讓不同 AI 分身各自改檔案不互踩）+ 跨 session 狀態管理 + 協調層防同檔衝突。原作者自己跑過 198 agents / 32 fleet sessions，merge conflict rate（合併衝突率）為 3.1%。
* **社群提出的 L6（系統自我改善）實作路徑**：透過 `SessionEnd` hook 自動提取行為模式 → 夜間 agent 聚合成新的 skills → 測試通過後自動升級。
