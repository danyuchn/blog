深夜拿到 Opus 4.8 新模型、Claude 的週額度剛好重置時，我很慶幸自己做的第一件事是：重整我的 harness。

因為很多人的直覺恰恰是反過來的：以為把所有踩過的坑、歷史教訓與業務規則全部寫進去，AI 就會更聽話。事實證明，規則塞得越多，常態注入把上下文窗口撐爆，模型反而抓不到重點，甚至連你最在意的那條核心規則都會漏掉。

## 一個把 1M 上下文用到 88% 的學員

我之所以認真面對這件事，源自前一天跟一位深度使用者的訪談。對方是一家公司的 COO，已經把 Claude Code 全面導入日常營運。他花了二十分鐘詳盡展示自己的工作環境：裡面裝了許多 MCP、自訂的 Skill，還串接了 Obsidian 知識庫，巨細靡遺地記下過往所有的決策重點與錯誤教訓。

但實際運用上，他發現模型沒辦法很好地協同調用這麼多工具。

我請他打開介面右下角的狀態，發現 Opus 的 1M 上下文已經被用到了 88%。往上翻閱對話，實際輪數才寥寥幾輪。一般來說，上下文使用量達到 60% 就應該主動觸發壓縮，88% 顯然極不正常。

當我請他輸入 `/context` 檢查，問題立刻現形：系統內建的記憶檔案（`CLAUDE.md`、rules、skills、hooks、memory）佔比微乎其微，幾乎沒有發揮作用；相反地，整個上下文全被大量知識庫文件強行塞滿。他強迫模型讀取所有他過去記下的「教訓」，但這些教訓大部分時候根本用不到。再加上處理長上下文任務時極少派出 subagent 分流，所有的資訊處理全部硬塞在單一主 agent 的視窗裡。

## 規則越加越多，模型為什麼反而不聽話

當大量無關的知識與雜亂規則被常態載入，上下文視窗會快速腐爛。隨之而來的，是模型執行任務的連貫性直線下滑，工具按需觸發的命中率也迅速劣化。這正是他覺得模型協同效率不好、又特別耗 token 的原因。

很多使用者的盲點，在於誤把「規則數量」當成「掌控程度」。每一條常態注入的規則，都在競爭模型的注意力。當設定檔裡充斥著敘事脈絡、範例背景與互相衝突的指示，模型反而抓不到重點，連你最在意的那條都會漏掉。

所以當午夜 Opus 4.8 推出、額度意外重置，我做的第一件事就是減肥我的 harness。

## 派一隊 AI 重整設定：六步精簡流程

為了給模型一個乾淨的執行環境，我切換到計畫模式，直接指派模型自己組隊體檢：

> 請你派儘可能多的 subagent，去調查我的 user-level、跟每個 project-level 的 `CLAUDE.md` / rules / hooks / memory / skills，找重複跟衝突，精簡常態注入，但以 harness 行為不變為最高原則。砍敘事脈絡（例子、人名、犯錯日期、範例），只留模型約束。

模型隨後規劃出了一套兼顧廣度與嚴謹度的六步清理流程：

1. 派出多個探索 agent，分別把全局與各專案的設定檔徹底掃描一遍，並對照官方文件查核最佳實踐。這裡必須堅持多 agent 平行分工，避免單一上下文被過多設定資料塞爆而出現調查失誤。
2. 逐一清理每個 harness 文件中的敘事脈絡，刪除人名、犯錯歷史與背景說明，只保留硬性的約束規則。同時將任務拆解為細粒度的待辦清單，防止跳步或漏檔。
3. 針對每個 Skill 的 description 進行精煉，確保觸發描述精準不冗餘。
4. 檢查設定檔中帶有 `@import` 的引用語法，將不需常態載入的文檔改為純路徑，避免每次啟動都被無端強制展開。
5. 派出多個 subagent，以四道嚴格的過濾關卡審查留下來的每一條規則：
   - 拿掉會不會犯錯？不會就果斷拿掉。
   - 是否只有特定檔案或資料夾才會用到？將其下放或改寫為路徑限定的規則檔。
   - 是否只與某個特定工具或流程相關？直接併入對應的 Skill 中按需加載。
   - 是否重要到絕對不允許違規？若需要硬性攔截，直接轉寫為 hook。
6. 引入文字嵌入模型為每一條約束建立語意向量，透過相似度計算找出意思重疊或互相抵觸的條文，徹底消除重複注入與衝突注入。

在執行過程中，每完成一個步驟，都會派出一個不繼承任何歷史上下文的全新 subagent 進行獨立驗收，確認無誤後才推進到下一步。

## 瘦身 36% 的具體成效與影片解析

經過這一輪重整，我的 harness 總行數直接減少了 36%，每次對話常態注入的 token 數量省下了一萬五千個。

也因為這樣，我用到現在的 Opus 4.8 都沒有特別感覺耗 token，速度甚至比之前還快——因為我已經幫它留好一個相對乾淨的上下文窗口，注入給它的是不衝突、不重複的精煉規範。

## 避免上下文污染的實務原則

除了清理常態設定檔，日常使用中最容易被忽略的上下文污染源，就是隨手把前一次對話的原始 JSON 紀錄直接整包倒給模型。

不是，為什麼要給它上一個對話的上下文 JSON。純 session history 裡面含有太多 tool call、output、flag 是無用的，就連 auto compact 的時候這些都會被摘除。

如果需要跨對話傳遞資訊，更好的做法是將上一輪的重點摘要提煉成簡短的臨時文件，或是依性質歸納進 `AGENTS.md`、規則檔、Skill 或 hook 中，讓各模組各司其職。

無論日常使用的是 Claude Code、Codex 還是其他工具，上下文管理與 harness 維護都是必須掌握的基本功。模型的上下文窗口再大，也不代表可以隨意堆放雜物。在把繁重任務丟給它之前，先給它一套不衝突、不冗餘的工作環境，才是讓 AI 穩定發揮實力的關鍵。

## 附錄

- 語意比對技術：在六步精簡流程的第六步中，使用 `gemini-embedding` 建立規則向量，藉由語意相似度比對找出跨檔案的重複與衝突約束。
- 跨工具維護：若在 Claude Code 與 Codex 之間切換工作，可透過自訂的 harness 同步腳本定期同步兩側的規則與設定，維持行為標準一致。
