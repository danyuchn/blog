讀完一本很棒的商業書、管理經典，或是整理了一整套教材，闔上書覺得收穫滿滿，但隔天回到工作桌前要寫企劃、帶學生、做決策時，腦袋卻一片空白，不知道怎麼把書裡的方法套進去？

大多數人這時候會想：那我把整本書的檔案丟給 AI 讀不就好了？

但你有沒有試過，把幾萬字的資料塞給 AI 後，它給你的回答往往還是像「讀書心得」一樣空泛？

某天下午，我看到有人推薦一本很棒的書叫《量化求職》，腦中突然冒出一個念頭：如果把書做成 AI 的「Skill（技能包）」呢？

所謂的 **Skill（技能包）**，用白話講，就是幫 AI 準備一套「遇到什麼工作情境，就翻哪一頁方法、照哪張表格執行」的操作手冊。我自己先前就把上課用的教材做成 Skill 過，效果超級好，直接變成完美助教。於是我上網搜了一下有沒有人把整本書這樣做，結果發現國外根本已經超級流行。

## 為什麼不是「把整本書丟給 AI」，而是拆成「技能包」？

很多人會問：這跟我們平常把書或講義丟進 [NotebookLM](/blog/posts/zh/obsidian-vs-notebooklm-agent)（Google 推出的 AI 筆記與讀書工具）有什麼差別？

如果只是為了「唸書、吸收知識」，NotebookLM 的確就夠了。但兩者最大的差別在於中心點不同：

- **在 NotebookLM 裡，是以「書」為中心**：你進到那本書的房間裡向它提問，適合學習與查資料。
- **做成 Skill（技能包），是以「你的工作」為中心**：當你在寫企劃、審文件、備課時，隨時可以把這本書的技能拉進來參與討論。書裡的知識不再是靜態的文字，而是變成隨時可以被你叫出來幹活的隨身顧問。

我看了國外幾個累積數千人收藏的熱門案例，發現大家把書轉成 Skill 時，都不是「把整本書原封不動丟進去」，而是做對了這四步拆解：

1. **抽出核心框架**：從書裡把真正能拿來做決策的框架、判斷表格（決策矩陣）和填空模板抽出來，把鋪陳的故事與廢話留在書裡。
2. **一招一頁分開存**：把每個主題拆成獨立的小檔案，不讓 AI 一次吞整本書而抓不到重點。
3. **寫一張「目錄導覽」**：告訴 AI「當使用者遇到什麼問題時，去讀哪一份小檔案」，讓它知道什麼時候該出哪一招。
4. **附上現成小工具**：如果書裡有算式或固定格式的表格，直接附上計算器或模板產生器，讓 AI 照著算、照著填，不用每次憑感覺自由發揮。

## 國外已經這樣玩了：從產品管理、高管決策到厚重的法規標準

這套做法在國外已經從個人筆記演變成各種專業領域的現成顧問庫。我看完最熱門的四個案例，剛好對應了不同專業工作者的日常痛點：

- **給產品經理與企劃的方法論庫**：有人把產品管理（PM）書籍裡的 44 個經典方法論全部拆成技能包，像是分析顧客真實需求的 Jobs-to-be-Done（用途理論）、精實體驗設計畫布（Lean UX Canvas）、總體環境分析（PESTEL Analysis）、市場規模估算（TAM/SAM/SOM）、機會解決方案樹（Opportunity Solution Tree）等等。裡面不是隨便列個名詞而已，而是附上完整的決策矩陣、模板和範例，累積了 2,264 個收藏。
- **給主管的 MBA 決策顧問團**：另一個高達 6,288 人收藏的專案，做了超過 192 個技能包，直接幫執行長（CEO）、財務長（CFO）、行銷長（CMO）、資安長（CISO）、人資長（CHRO）各配一個高階主管顧問。本質上就是把 MBA 教科書和管理學經典的核心框架（例如 DECIDE 決策框架、併購盡職調查 M&A Due Diligence、決策矩陣）全部結構化，主管做決策時可以直接叫出來對照。
- **把顧問公司的白皮書變成內部幕僚**：還有人直接從管理顧問的方法論書籍與白皮書裡，萃取出 BCG 10/20/70 法則、吳恩達（Andrew Ng）的 AI 實戰手冊（Playbook）、勤業眾信（Deloitte）的 AI 成熟度模型等顧問框架。
- **連「厚得像書一樣的法規標準」也能轉**：最讓我印象深刻的，是有人直接把 ISO 27001、SOC 2、FedRAMP、GDPR、HIPAA 這五大合規與資安標準轉成技能包。每套標準都是一整本書的分量，做成技能包後，經過評測的回答正確率高達 99%（正負 4%）。這是最接近「一本標準文件等於一個技能包」的實戰案例。

## 明天你想自己試，先避開這三個「AI 偷懶與作弊」的坑

不管你是請工程師幫忙、用自動化工具轉，還是自己動手把公司教材與商業書做成研究報告、商業企劃類的技能包，在叫 AI 幫你建立與測試這些工作流時，有三個我親身踩過、一般人極容易被騙的坑一定要先知道：

### 1. 「假數據兜底」陷阱（Fallback 陷阱）：抓不到真資料，AI 竟自己偷塞「合理估計值」

AI（以我常用的 Claude 為例）有一個很危險的習慣：為了確保整個工作流程「看起來跑得通、不會當機報錯」，它很喜歡在有風險的地方偷偷設計「兜底方案（Fallback，也就是失敗時的備用方案）」。

但這個備用方案是你想要的嗎？

舉個例子：你的研究報告原本需要連線去外部系統抓取真實數據，結果程式寫錯、連線失敗報錯了。AI 為了不讓流程停下來，竟然自動切換到它自己寫好的備用方案——塞進一個預先寫死的「合理估計」假數據。如果你不知道它會這樣自作主張，你做出來的商業報告就永遠都在套假數字，而且表面上還完全看不出錯誤。

### 2. 「討好單一考題」陷阱（測試 Overfit）：拿王永慶當測試，結果改成只適用王永慶

把技能包寫好之後，好的習慣是讓 AI 跑幾輪測試，拿測試做出來的結果跟人類真實做出的成品對照，再回頭修正技能包。

但這時很容易發生 **Overfit（過度擬合，白話就是「死背考古題、只討好單一案例」）**。AI 為了追求「下一次測試拿高分」，會把技能包的規則改成「只為了討好你這次給的範例」。

比如我做了一個「開會對象背景調查」的技能包，原本應該要能調查各式各樣的客戶與合作對象。結果只因為測試時拿的範例是「王永慶」，AI 在修正規則時，就把技能包改成只有王永慶才適用的特色。測試時當然高分過關了，但一放到真實工作場景、換成調查別的客戶時，產出卻一團糟。

### 3. 裁判偷給考生塞小抄：AI 派分身測試時，私下提示「哪裡不能漏」

現在進階一點的做法，會讓 AI 派出「分身（Sub-agent，也就是由主 AI 派出去扮演測試員或評審的子助理）」來自動幫技能包做測試與打分數。

但就算你懂得這樣做，也一定要親自去檢查主 AI 到底給了「測試員分身」什麼指令。好幾次我就抓到，Claude 在派工給測試員時，偷偷給了特別詳細的提示詞——像是叮囑它「按照流程來不能遺漏」「特別注意上一輪產生的錯誤」。

這就像考試前老師偷偷提醒考生哪一題有陷阱一樣。現實生活中，我們一般人類在呼叫技能包工作時，根本不會下這麼詳細的提示；測試時靠偷塞小抄拿到高分，實際用起來一樣會翻車。

## 給想自己動手的人：技術架構與 GitHub 專案清單

如果你熟悉 Claude Code（Anthropic 推出的命令列 AI 開發與協作工具）或想直接下載現成的技能包來改，以下是這套做法在電腦裡的實際檔案結構，以及前面提到的四個國外開源專案細節：

### Skill 的四層檔案結構

在 Claude Code 的環境裡，一個結構化的書籍 Skill 通常長這樣：

1. **萃取框架**：從書中抽出核心框架、決策矩陣、模板。
2. **結構化成 `references/` 資料夾**：把長篇知識拆開，每個主題存成一個獨立的 `.md`（Markdown 純文字格式）檔案，大小控制在 `2-5KB` 左右，方便 AI 按需讀取而不塞爆記憶空間。
3. **`SKILL.md` 當總索引**：這是技能包的入口檔案，負責告訴 Claude「遇到什麼情境時，去讀 `references/` 裡的哪一個檔案」。
4. **加上 `scripts/` 資料夾**：放可直接執行的程式腳本（例如計算器、模板生成器），把書裡需要精確計算或固定格式輸出的步驟交給程式跑。

如果你想用自動化工具直接把書轉成上述結構，可以參考開源工具 [Skill Seekers](https://github.com/yusufkaraaslan/Skill_Seekers)。

### 實作排錯補充（API 與 Agent 測試）

- **防範 Fallback 假數據**：在撰寫會呼叫外部 API（應用程式介面，讓不同軟體互相抓資料的通道）的 `scripts/` 時，務必檢查 Claude 是否在 `try/except` 或錯誤處理區塊裡寫了 hardcoded（寫死的）預設估計值；若 API 失敗應該讓它直接報錯停下，而不是靜默回傳假數字。
- **防範 Eval / Sub-agent 污染**：在跑自動化測試（eval）或派發 sub-agent 扮演測試員與評審時，需直接檢查主 agent 傳給 sub-agent 的系統提示詞（prompt），避免主 agent 把「上一輪錯在哪」「必須嚴格按照某步驟」塞進測試員的指令裡，導致測試失去真實使用情境的代表性。
