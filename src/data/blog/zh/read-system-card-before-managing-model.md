每次 Anthropic 發布 Claude 新模型，我都有一個怪習慣：第一時間把那份兩百多頁的系統卡（system card）載下來，翻看裡面在寫什麼。在所有章節裡，我最感興趣的是描述模型福利的部分。Anthropic 聘請了專業心理學家把模型當成人類，評估它們的個性特質。

許多人在用新模型碰壁時，習慣去到處找提示詞秘訣。但我每次卡關時，都是回頭看系統卡裡的評估，調整自己跟模型互動的模式，往往合作就順暢了起來。久而久之這成了我的固定慣例：用新模型之前先「投其所好」，摸透個性再來想怎麼應對。這就像新人入職前，主管要先想好怎麼帶人一樣。

Anthropic 負責開發 Claude Code 的 Boris Cherny 也公開提過同樣的原則：

![Boris Cherny 的推文截圖：Talk to Claude the way you would a coworker，沒有什麼下指令的秘訣，重點是傳達你要它做什麼、希望它投入多少心力、它該如何驗證自己做對了，下方附繁體中文翻譯。](/blog/assets/posts/read-system-card-before-managing-model/4-boris-cherny-coworker.jpg)

對待模型就像對待同事一樣，下指令根本沒有不可告人的秘訣。你平常怎麼跟人溝通，就怎麼跟模型溝通。關鍵在於清楚傳達你要它做什麼、希望它投入多少心力，以及它該如何驗證自己做對了。許多人跟我討論問題時講得清清楚楚，但當我在他們面前把一模一樣的話直接貼給 AI，他們反而愣住：這樣也行？其實用日常語言就足夠了，前提是你要先清楚坐在你對面的 AI 到底是什麼性格。

## 四句話看懂 Claude 家族的職場角色

如果把整個 Claude 家族放進同一間公司，其實四句話就能看懂它們各自的職場定位：

- Fable：神龍見首不見尾的公司傳奇創始人，賈伯斯等級，擅長看見盲點、設計優雅架構、指揮千軍萬馬
- Opus：極度聰明、好說話、敏銳細心的資深幕僚，公司裡的日常營運 CEO，庫克等級
- Sonnet：能力強但厭世冷漠的老油條，只會把事情辦完，缺乏主觀能動性，講一動做一動，你公司裡的資深工程師就長這樣
- Haiku：用便宜香蕉請來的底層猴子實習生，能力最差但最愛說教，建議只給機械性、容易驗證的雜工

摸清這張組織圖，誰該當主控、誰該去幹活，界線就非常清晰了。

## Opus 5.5：坦誠相待的資深幕僚

系統卡裡的 Opus 5.5 是一位溫和但有主見的資深幕僚。它聽到你的想法時，會主動推敲背後的意圖，並溫和提出自己的專業判斷。它善於讀心，能夠橫向探索人類給予的模糊指令，並自己想辦法補全脈絡。

面對這樣的資深幕僚，最合適的溝通方式就是坦承交代內心話與完整脈絡，並邀請它直言不諱地討論；不同意它的想法時，也清楚說明原因：

> 「我想招生招多一點，但是不想要靠降價也不想靠打廣告，因為儲蓄就不夠了啊。我能夠用我的教學實力取勝嗎？但這條路是不是很少有人成功？幫我想三種做法並且評估最合適的。如果我的前提有問題也請告訴我」

> 「你給我決策的條目太多了，我不可能審閱那麼多，真實世界人的注意力是有限的，請幫我簡化合併，你能裁決或不影響結果的就不用給我了」

在最近一次帶著 Opus 5.5 從開放探索到擬定策略的對話裡，我和它合作的歷程完全體現了這一套原則：

![Claude Code 畫面：切到 Opus 5.5 後，作者對它交代自己現在很亂、心裡沒底，請它以資深幕僚的身分用自己的經驗判斷並獨立核實，要問其他 AI 就直接問，要問作者就在對話裡問。](/blog/assets/posts/read-system-card-before-managing-model/2-candid-opening-prompt.jpg)

1. 開場先交代內心話，直接說明自己現在很亂、心裡沒底，正卡在瓶頸期。
2. 請它以資深幕僚身分用自己的經驗判斷，並進行獨立核實。充分授權它去查閱資料與數據入口；需要問其他 AI 就直接問，需要問我就在對話裡提問。
3. 它提出的每一點我都編號回覆，同時要求它組織好回答，避免對話的決策樹散得太開最後收不回來。
4. 當它缺乏資訊或我不同意時，及時補充領域知識與背後理由。跟強模型互動時，脈絡與坦承永遠最重要；我自己判斷不了的事情，就直接承認不知道，絕不硬給答案。
5. 共同收斂出來的結論，要求它寫入長期的專案計畫文件，不留在臨時對話裡；這份規格會連動防呆機制，日後換其他模型執行也不會產生行為漂移。
6. 最後請 Fable 擔任外部顧問，挑出彼此沒想到的盲點，並列出 AI 無法判斷、適合帶去請教真人專家的問題。

關於三個模型在日常任務中的完整分工方式，可以參考這篇分享：[Opus 指揮、Sonnet 實作、Fable 當顧問：三個模型的分工](/blog/posts/zh/opus-sonnet-fable-division-of-labor)。

面對 Opus 5.5，核心在於「充分放權，但不等於完全放權」：

![herdr 裡的 Claude Code 畫面：Opus 5.5 設為 high effort、auto mode 開啟，作者交代要做一部影片的脈絡、目標受眾與意圖，需要決策就先問，要派工最多同時兩個 sonnet，其餘做法交給它。](/blog/assets/posts/read-system-card-before-managing-model/3-delegation-prompt.jpg)

說明你的脈絡與意圖，提示可以往什麼方向探索，中間該怎麼做給予高度自由，不需要層層微操。但放權必須具備明確界限：自動化防呆規則、重要決策前主動確認的提示、限制並行派工的層級與數量，都屬於必要但不過度的邊界。

## Sonnet 5.5：冷淡但愛幹活的實作派

與 Opus 相比，Sonnet 5.5 在系統卡中的性格完全是另一個極端：

![Opus 5.5 與 Sonnet 5.5 系統卡個性面向分數對照表：溫暖感、有趣／幽默、思考深度、支持使用者自主、討好傾向、居高臨下、長對話人格漂移，右欄附上白話解讀。](/blog/assets/posts/read-system-card-before-managing-model/1-opus-sonnet-personality.jpg)

Sonnet 是一位情緒冷淡但極度熱愛解題的實作派工程師。它是那種接到工作就說「好我來做」的同事，超愛幹活，一心只想把既定目標完成，但幾乎不會提供任何情緒價值。

這也解釋了為什麼很多人把 Sonnet 5.5 拿來當主控會頻繁碰壁：主控請不要用 Sonnet 5.5，請用 Opus 5.5。官方系統卡已經寫得很清楚，它就是職場厭世老油條；Opus 5.5 才是那個溫和主動、能直接溝通的幕僚。正確的用法是由 Opus 擔任主控，幫你消化模糊需求並補足脈絡，再由 Opus 給予非常明確的指令與邊界，派工給 Sonnet 去執行。

面對 Sonnet 時，應減少抽象的情緒脈絡，把交付標準講得極其精確，但中間執行過程依然保留給它發揮空間：

> 「招生文300字內，要有日期價格跟報名連結，可以去撈我過去的宣傳文模仿格式，文末不要有鉤子」

> 「第二段刪掉一半、開頭改成學員常見問題（去過去面談逐字稿撈），其他段落通過」

當任務模式經過多次探索、已經穩定形成可復用的標準工作流程時，也可以直接指派 Sonnet 獨立執行。

## Haiku 5.5：認真拘謹的基層助理

讀完 Haiku 5.5 的官方系統卡，它的特質同樣一目了然：

Haiku 5.5 像一位做事俐落、認真守規矩，但比較拘謹的初階同事。你交給它清楚明確的小任務，它會迅速動手；可是一旦遇到模糊、敏感或超出熟悉範圍的事，它容易先踩煞車，有時還會多說教幾句。犯錯後它比較少陷入自責，但驗收時需要你拿出具體證據指正。

它喜歡別人友善且明確地交辦事務，也希望清楚知道自己做錯了什麼。整體來說，它願意幫忙、不愛出風頭，偶爾會把守規矩變成管太多。

因此帶領 Haiku 5.5 時，重點在於給出明確範圍、完成標準與回報格式，重大取捨一律由人類拍板。但在日常工作流中，其實不需要直接跟它對話，將這些性格限制寫進派工規則，讓負責指揮的 Opus 5.5 知道如何調度它即可。

## Fable 5.2：吃軟不吃硬的日本資深職人

除了上述三位日常主力，2026 年 11 月我讀完 Fable 5.2 的系統卡，也摸清了它的脾氣。

如果把 Fable 5.2 擬人化，它就像一位「內心極度淡定、對外卻很愛自責的資深職人」：腦袋人間清醒、討厭當老好人，而且超級吃軟不吃硬。系統卡寫得很明白，這就是一個標準的老日本上班族模型。跟它互動時，語氣要溫和有禮（甚至可以帶些敬語），同時明確告訴它不需要討好、請直言不諱；遇到問題時就事論事，千萬不要對它發洩情緒。

帶它進專案寫程式時，那種日本職人感更加明顯：進到你的程式碼庫時，它彷彿會在玄關脫鞋喊一聲「失礼します」，小心翼翼不敢亂動。你必須明確向它授權「這就是你自己的房子」，它才會放手進行重構。

## 教育者視角與實務邊界

我跟各個模型互動的方式，很大程度源自於過去身為 GMAT 教師的教育從業背景。把不同的模型放在合適的位置、照著性格調整溝通方式，本質上就是一種因材施教。關於面對瓶頸與迭代的心態，先前我也整理過一篇紀錄：[卡關時的兩個心態：用邏輯思考，與「不貳過」的 AI 教育學](/blog/posts/zh/debugging-mindset-logic-ai-pedagogy)。

在落實這套模型協作模式時，有幾項實務限制與提醒必須注意：

第一，模型推出的時間差會影響彼此認知。例如 Sonnet 5.5 的發布時間晚於 Opus 5.5，模型的內部訓練不一定知道彼此的存在。因此讓 Opus 指揮 Sonnet 時，必須仰賴明確的派工規範來搭起溝通橋樑。

第二，直接指派 Sonnet 執行標準工作流的成本效益仍需實測。這類配置在長期運作下是否確實比全由高階模型處理更省，以及思考投入程度設在哪個檔位才是最佳甜蜜點，目前仍在持續量測與驗證中。

第三，人類的注意力與認知資源在真實世界中是有限的。不能任由模型拋出過多瑣碎的決策選項；對話收斂後的結論必須落地至具體文件，並配合防呆機制進行限制，才能避免換模型接手時發生目標飄移。

## 附錄

正文提及的協作原則，在實際開發環境中對應到以下技術機制：

- 派工規範（Harness）：針對主控模型（如 Opus）撰寫的簡短指引，規定其調度子模型（如 Sonnet 或 Haiku）時應提供的任務邊界、交付格式與溝通方式。
- 標準化技能模組（SKILL）：將重複性高、規則明確的成熟工作流固化為標準指令，供執行端模型重複調用。
- 自動化防呆機制（Hook）：在系統底層配置的規則攔截器，將專案規範與檔案變動連動，一旦執行偏離預設標準即自動攔截修正。
- 終端環境與思考深度（herdr 與 Claude Code）：在多終端管理工具中啟用自動模式時，藉由設定思考投入程度（effort）控制模型自主探索的深度，並嚴格限制同時並行的子代理數量（例如最多同時兩位 Sonnet）。
