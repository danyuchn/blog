# 技術分享文規格（Tech Share Post Spec）

適用：作者自己做的工具、外掛、流程、系統，寫成「我怎麼做出來、有沒有用、你怎麼做自己的版本」的長文。
不適用：社群貼文改寫（走 article-spec 改寫原則）、週報、短觀點文。
通用欄位、檔名、圖片路徑、私人名字去識別化一律以 `article-spec.md` 為準，本檔只規範這一類文章的骨架與紀律。
範本文章：`src/data/blog/zh/work-mode-ai-working-modes.md`（2026-10-25）。流程見 `.claude/skills/tech-share-post/SKILL.md`。

## 1. 骨架（順序固定，H2 分節）

作者原話（2026-10-25 /goal）：「文章的脈絡是要先講我的痛點，再來說我希望解決的情境跟開發的過程，再來是我的實測，然後是開發時用了什麼提示詞，讓讀者看到也可以根據他們的情境自己做。不要有太多技術術語。」

1. **開場兩段（無標題）**：第一段一句話講它是什麼；第二段預告後面幾件事，並放一個站內錨點連到技術附錄。
2. **痛點**（H2）：至少 3 個，每個都要有真實情境。次數與統計必須是查過紀錄才寫的數字，附作者原話。
3. **希望的樣子與演進**（H2）：先講最終形態，再按日期列關鍵轉折。只講對讀者有用的轉折，不講改名、內部代號這類歷史。
4. **實測**（H2）：先寫範圍與基準（幾場、幾回合、跟什麼比），再每個效果一段。每個效果旁邊緊接限制與不確定處（混淆因素、估算方式）。效果小或沒效果也要寫。
5. **開發時下的提示詞**（H2）：6–8 則作者原話，用 `>` 引言逐字不改（可小幅刪節並標明）。每則前有短標題，後有一句「換成你的情境」。
6. **起手提示詞範本**（H2）：一個 `text` 程式碼區塊，5–6 步，括號留給讀者填。
7. **附錄：技術做法**（H2，內含 H3）：給想自己實作的人。見第 4 節。
8. 不寫小結、結語或總結昇華；範本或附錄的最小版本之後就結束。

## 2. 數字與引言紀律

1. 數字只能來自可查的分析檔、紀錄或原始碼；查不到就不寫，不補、不估。正文數字改動時，含數字的圖要同步重畫。
2. 作者原話逐字引用；英文版逐段加 `> (translated from Chinese)`。
3. 估算值要講明是估算與方法（例：「換算下來約…，是估算」）。
4. 圖與影片若不是真實截圖而是依紀錄重建，正文用一句話註明「依實際對話紀錄重建」。

## 3. 語氣

1. 正式口語的第一人稱，句子短，轉折用「但／不過／其實」。
2. 正文少術語：hook、系統提示、快取之類改白話；指令名稱與產品名保留原樣。術語集中放附錄。
3. 禁「不是 A 而是 B」、金句、排比、emoji、「讓我們」。寫完跑 `threads-voice/scripts/check_draft.py check --acct 主帳 --mode 資訊`，「必改」項照改（「提示」項自行判斷）。
4. 潤稿（若用外部模型）只能做保守修飾，數字、引言、程式碼、圖片行不得變動；改完用腳本比對數字集合與引言行。

## 4. 技術附錄

1. 以原始碼為準，不憑印象；每個技術陳述要能對到 檔案:行（寫作時留在回報裡，不放正文）。
2. 建議的 H3：整體架構、一則請求的生命週期、狀態放在哪、參數與規則、閘門或錯誤處理、測試與驗證、想自己做的最小版本。
3. 圖至少三種：事件順序（時序）、判斷分支（流程）、狀態變化（狀態機）。技術讀者要看的是順序、資料流、哪裡有狀態、哪裡被擋。
4. 程式碼用最小可運作的版本，不貼整檔；不含本機絕對路徑、IP、帳號。

## 5. 圖與影片

1. 圖：依 `article-spec.md`「主動配圖」；本類文章正文 3–5 張，附錄可再加 3–4 張。
2. 影片（選用，示範狀態切換或輸出變化時才做）：
   - 長度 ≤30 秒、1280×720、檔案 <1MB；放 `public/assets/posts/<basename>/demo.mp4`，另附 `demo-poster.jpg`。
   - 做法見 `.claude/figure-kit/video/README.md`；影格放 `mktemp -d`，不要放進 repo。
   - 內嵌：`<video controls preload="metadata" playsinline poster="…/demo-poster.jpg" style="width:100%;height:auto;"><source src="…/demo.mp4" type="video/mp4"></video>`，緊接一句重建註記。

## 6. 隱私與公開前檢查

1. 不得出現：客戶與學員名、私密專案名、內網 IP、本機絕對路徑、信箱、憑證、額度帳號細節。
2. 先以 `draft: true` 讓作者審；審完才改 `draft: false`，`pubDatetime` 用已過去的 UTC 時間。
3. 發布前：`npm run check:private`、`npm run check:content`、`npm run build`；en 圖不得有中文；圖與影片大小合理。
4. push 等於發布，等作者明說才 push；發布後 curl 線上網址驗證 200，並檢查是否與舊文主題重複（重複時舊文只改該段為一句摘要加連結，不整篇刪）。
5. 對外貼連結帶 UTM，規則見 KB memory `feedback_blog_link_agentcrew_url`。

## 7. 雙語

1. 一律先寫 zh、定稿後再翻 en；段落、H2、圖的順序一一對應；附錄錨點 zh `#附錄技術做法`、en `#appendix-how-it-is-built` 這類 slug 要自己用 github-slugger 驗過。
2. 本類文章的 en 版以 agy 翻譯＋逐項核對數字、引言、程式碼為準，不另跑 `/humanizer`（見 `content-workflow.md`）。
3. 圖檔 zh 用 `N-name.jpg`，en 用 `N-name-en.jpg`；title／description／alt 各自在地化。
